# 第 283 轮：「一条差评全自动处理」场景 — 能力缺口清单

> 起因：老板贴了一段演示文案（收到差评 → 定位订单 → 客服 Agent 出话术 → 根因预警 → 归档复盘），
> 问「目前应该还实现不了吧？这个真实场景我这个项目还缺什么能力？」
>
> 本文是**代码取证**结果，不是评估意见。每条结论都带 `文件:行` 锚点，可复核。
> 取证日期：2026-09-27。

---

## 〇、一句话结论

**做不到，而且不是"差一点"** —— 演示里 7 个环节，能真跑的只有 4 个**动作**
（`switch_agent` / `open_view` / `create_ticket` / `search_faq`），
而演示真正卖的**信息整合**（订单 → 物流 → 差评 → 话术 → 竞品 → 规则）
**在数据库层就没有**。缺的不是编排，是**原料**。

---

## 一、最容易误判的一处：本仓的 `review*` 全是「复盘」语义，不是「差评」

场景里说的「差评」是买家评论（customer review）。但本仓所有 `review` 前缀的东西都不是它：

| 名字 | 真实语义 | 锚点 |
|---|---|---|
| `review_analyst` Agent | **运营复盘师**：周报 / 月报 / 广告归因 / 商品表现 / 库存健康 / 利润审计 | `modules/review_analyst/agent.py:129-136` |
| `list_reviews` 工具 | 列出**复盘库里已归档的历史复盘** | `modules/review_analyst/tools.py:287-311` |
| `review_reports` 表 | 运营复盘报告快照（幂等键 = 店铺+类型+周期+周期末日） | `modules/review_analyst/db_model.py:100-118` |
| `review-*` 4 条技能 | 复盘叙事 / 月度摘要 / 广告归因 / 行动计划 | `modules/skills/seed.py:1114/1169/1222/1277` |

⇒ **仓库里没有任何一张表、任何一个工具产出「买家评论文本」。**

这条不是我推断的 —— 本仓**第 188 / 189 轮已经踩过一次**，并把结论写进了代码注释：

> `modules/skills/seed.py:332` —— 「**智能客服**的对话上下文里是 FAQ / 订单 / 工单，**不读评论** ⇒ 挂了也取不到原料」
> `modules/skills/seed.py:189` —— 「它的 6 个工具没有一个产出评论数据，system prompt 里也**不含「评论」二字** ⇒ 点了这张卡，Agent 手里根本没有原料，只能凭想象编」

当时 `review-pain-mining`（评论痛点挖掘）因此被从客服 / 复盘师挪走，最终挂在 `competitor_intel`（它有 `analyze_competitor_reviews`，但那是**竞品**的评论）。

## 二、逐环节对照

| 「包装类型」 | 无此字段 | ❌ |
| 「历史同 SKU 差评数」 | **无差评数据源** | ❌ |

### 步骤 2：智能客服 Agent

| 演示说 | 现状 | 判定 |
|---|---|---|

★ **最尖锐的一处自相矛盾**：`cs-refund-playbook` 的正文第 0 步要求
「按**证据**判断责任归属，引用订单 / 物流 / 图片证据」，
而它挂在智能客服名下，锚工具只回填到 `search_faq`（`seed.py:1911`），
智能客服的全部家当只有 4 个工具（`tools.py:131-167`）：

```
search_faq / create_ticket / analyze_sentiment / get_conversation_summary
```

⇒ **技能要求证据，工具集给不了证据**。点了这条技能，模型只能在「没证据」和「编证据」之间选。

## 三、缺什么能力（按 P0 / P1 / P2）

### P0 — 没有它，这个场景一个字都开不了口

**1. 买家差评数据源**（根）
- 建 `customer_reviews` 表（`shop_id` / `asin` / `sku_id` / `order_id` / 星级 / 正文 / 评论日期 / 归因标签）
- ★ 接入是**硬约束**：亚马逊 SP-API **没有** Reviews API（已对第三方关闭），可行路径只有三条：
  | 路径 | 说明 | 代价 |
  |---|---|---|
  | 卖家后台导出 CSV → 上传 | 最合规、最可控 | 人工，非实时 |
  | 第三方数据服务（Keepa / Helium10 / Jungle Scout） | 有 API，能拿评论 | 付费 + 数据出境合规 |
  | 自研爬取 | — | **违反平台 TOS**，封号风险，不建议 |
- 建表之前先拍板走哪条路径，路径决定表结构（增量同步 vs 全量快照）

**2. 订单 + 物流数据源**
- 建 `orders` / `order_items` 表（SP-API `get_orders` / `get_order_items` **封装已就绪**：`platforms/amazon/sp_api/orders.py`、`sp_api_source.py:224-234`）
- 现状：封装有了，**没有落库表、没有定时同步任务**
- 物流轨迹需 Shipping API 或 17Track（Orders API 明确不返回运单号 / 承运商）

**3. 客服 Agent 补工具（成本最低的一条）**
- `fetch_order_tracking()` 已经写好，注释就写着「客服场景 [新增]」（`base.py:17`、`sp_api_source.py:529-551`）
- **只差接线**：挂进 `customer_service_tools`
- 这是全清单里唯一一条「代码已就绪、只差一步」的

### P1 — 让闭环能真的闭

4. **差评归因打标**：复刻 `review-pain-mining` 的三分类（产品问题 / 描述不符 / 物流售后），作用在**自家**评论上
5. **补偿规则引擎**：可配置的额度上限表，替掉技能正文里那句「不超授权」的空话 —— 现在 Agent 既不知道授权上限，也不知道历史标准
6. **产品 / SKU 健康分**：独立于广告的 `health_score`，定义扣分来源
7. **`cs-refund-playbook` 的证据闭环**：把上一步的订单 / 物流 / 差评工具回填进它的 `tools`（现在只有 `search_faq`）

### P2 — 演示里那些"显得很聪明"的动作

8. 竞品包装 / 视频取证（现有竞品快照字段里没有）
9. 成本 - 破损率预测模型（需要供应链成本数据，本仓无）
10. 中英双语 + 敏感词过滤（纯实现活，随时可做）

## 四、分档方案

| 档 | 内容 | 能演示到什么 | 不能演示什么 |
|---|---|---|---|
| **A. 最小可演示** | 差评 CSV 导入 + `customer_reviews` 表 + 客服挂 `fetch_order_tracking` + 一条差评处理技能 | 「粘一段差评文本 → 定性责任 → 出话术 → 建工单」 | 历史差评率、重复问题判定、物流证据（无轨迹源） |
| **B. 真闭环** | A + 订单落库同步 + 归因打标 + 补偿规则 + SKU 健康分 | 演示里步骤 1/2/4 基本成立 | 竞品包装取证、破损率预测 |
| **C. 完整演示** | B + 竞品包装视频取证 + 成本模型 + AIGC 对比图 | 全链路 | — 取决于外部数据源采购 |

**建议走 A → B**：A 档的产出（差评台账 + 归因标签）本身就是 B 档的输入，不做废工。

## 五、一条该记的教训

这段演示文案如果**对外**发出去，属于「虚构能力」。而本仓第 283 轮前三项
（跨租户越权、输出校验止血、提示词版本管理）干的恰恰是**清伪成功** ——
`structured_chat` 解析失败退化成 `{"raw_text"}` 导致 `enhanced=True` 假成功、
工单号「创建成功」但刷新就没了（`cs_tickets` 建表前的旧行为，见 `db_model.py` 开头）。

**同一个病，两种形态**：
- 代码里是「失败了但返回成功」
- 文案里是「没做但写成像做了」

后者更难查，因为它不住在代码里 —— 判据只能是「这条能力的数据源在哪张表」。
⇒ 建议把「**演示文案里的每个名词都要能指到一张表或一个工具**」写成一条硬规矩。
