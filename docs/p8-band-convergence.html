一句话结论：机制已统一到单一真源、数值除「两处产品行为变化」外逐值逐色零变化； 原有 7 种阈值不是被并成 1 套，而是被拆成 18 套具名口径， 每套带 note 写明用途与后端真源出处 —— 以后没人能再把「广告健康」和「商品监控健康」误并。

1. 为什么「阈值不统一」是缺陷，而不是风格差异

最毒的不是阈值多，而是同名不同阈值与跨端分叉这两件事。

1.1 同名不同阈值 —— 改一处以为改了全部

改造前全库散落着多组互不相同的阈值，其中同名函数 getScoreColor 在 4 个文件里用了 3 套阈值： 70/40（蓝海结果 / 蓝海抽屉 / 选品库）、80/60（SEO 诊断）、75/50（行内版）。 维护者调「评分配色」，实际只改了 1/3。另有同名不同值的长尾：relevance 在关键词挖掘是 90/75、 在列表配置里是 90/80；acos 在广告看板是 35/25、在评论配置里是 33/25。

1.2 跨端分叉 —— 后端报问题，前端显绿 已修

真实缺陷：后端 ad_analysis/agent_ad.py:902 用 worst_campaign.health_score < 50 生成「Campaign 表现差」告警、并建议暂停；前端 AdDiagnosisResult 却用 80/60 上色。 → health_score = 55 的 Campaign 后端判定为「有问题」，前端仍显示橙色/绿色。 这是跨端语义分叉，不是配色偏好。

1.3 为什么不能「统一成一套阈值」

阈值不只管颜色。后端 blue_ocean >= 70 决定 premium 计数、>= 50 是过滤线、 health_score < 50 触发告警；前端 relevance >= 90 决定「推荐词」标记。 所以改阈值 = 改业务判定 = 改告警灵敏度 = 产品决策。 把 4 套不同的阈值硬并成一套，会让 72 分的「良」变成「中」—— 那是产品改版，不是重构。

本轮采取的口径（也是老板拍板的口径）：
① 机制统一：阈值 / 档位名 / 档位色只在一处出现，调用点显式声明「我用哪套口径」；
② 数值不乱动：A 类（后端为真源）保持原值，C 类（反向 / 异量纲）各建一套；
③ 仅两类必须动：跨端分叉（对齐后端真源）+ 同名不同值（统一为一个值）—— 这两类单独列出来待老板确认。

3. 真源设计：theme/bands.ts

3.1 BandDef 字段

type BandDef = {
  scale: readonly [number, number]   // 量纲区间，仅作文档与防误并用；不参与计算
  dir:   'higher' | 'lower'          // higher=越大越好；lower=越大越危险（反向指标）
  cmp?:  '>=' | '<='                 // 阈值比较方向，决定 cuts 排列方向与边界归属（见 §4）
  cuts:  readonly number[]           // 分界阈值 -> 共 cuts.length + 1 档
  keys:  readonly string[]           // 档位名，与 cuts 一一对应（higher 天然「最好→最差」）
  colors:readonly string[]           // 档位色，与 keys 等长同序（CSS 变量表达式）
  note:  string                      // 用途 + 真源出处 —— 防误并的最后一道闸，必填
}

3.2 三个出口

出口返回典型用法
bandColor(name, v)档位色（CSS 变量表达式）:stroke-color="bandColor('score', r)"
bandOf(name, v)档位名（字符串）bandOf('acos', g.acos) → 'ok' | 'warn' | 'bad'
bandIndex(name, v)档序号（0 起，可数组查表）ROI_TAGS[bandIndex('roi', r)]
 
export function bandIndex(name: BandName, value: number): number {
  const b = BANDS[name]
  const v = Number(value)
  // NaN 兜底按方向分：higher 落末档（最差）、lower 落首档（最危险）—— 都落「最差」侧，宁误报不漏报
  if (!Number.isFinite(v)) return b.dir === 'higher' ? b.cuts.length : 0
  const cuts = b.cuts as readonly number[]
  const ge = (b.cmp ?? '>=') === '>='
  for (let i = 0; i < cuts.length; i++) {
    if (ge ? v >= cuts[i] : v <= cuts[i]) return i
  }
  return cuts.length
}

4. 两个必须讲清的实现细节

4.1 ★ cmp 字段是必需项，不是洁癖

边界等号的归属是会变的。原写法 acos <= 25 ? 'ok' : …（升序、含等号）与 「降序 >=」写法在 acos = 25 时给出不同档位。 我在第一轮改造时用了降序写法，等价性探针立刻报出 acos@25: success→warning、 acos@35: warning→danger 两处串档。
→ 解法：cmp:'<=' 时 cuts 必须升序、比较用 v <= cuts[i]。 不要靠改写不等式糊过去 —— 那会静默改变边界归属。修复后边界精确： 0:ok 24:ok 25:ok 26:warn 34:warn 35:warn 36:danger 100:danger。

4.2 ★ 防误并三条铁律（写进每套 note）

  1. 同名 ≠ 同指标。campaignHealth（广告 Campaign 健康）与 monitorHealth（商品监控健康度） 区间相同但语义无关 → 不可合并。UI 文案也必须区分，否则用户以为是同一个分。
  2. 量纲不同不可并。0–100 / 0–1 / 0–5 / 0–10 各自成套。把 sentiment（0–1）并进 score（0–100），会让「0.8 分的情感」被当成差评。
  3. 方向不同不可并。usage / share / cr4 / acos 是反向 （越大越危险）。并进正向档会把「风险高=红」和「机会大=绿」缝在一起，出来的颜色是反的。

8. ⚠️ 需要老板确认的两类「产品行为变化」

以下改动不是零变化。它们改变了阈值，因此改变了产品行为。我按「跨端必须一致 / 同名必须同值」的原则做了收敛，请你确认是否接受。
改动原 → 新行为影响状态
① campaignHealth 红界
