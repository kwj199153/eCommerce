# 侧栏「矮视口紧凑档」— 第 377 轮

> 老板原话：**「在 pad 中，左侧边栏不能完全看见，要下滑；能不能一页可见（比如将字体缩小？）是否可行或者有其他更好的方案」**
>
> 结论先说三句：
> 1. **缩字体不可行** —— CDP 实测省 **0px**，因为行高写死 34px，字号不参与占位；
> 2. 真正缺的是 **37px**，压**行高 + 标题**就够（省 94px）；
> 3. 触发条件必须挂在**高度轴**（`max-height: 860px`），不是继续用宽度的 1100。

---

## 一、实测：到底缺多少

工具：`.workbuddy/probes/cdp-sidebar-fit.mjs`（起真实 dev server + headless Chrome，四档视口逐个量）。

侧栏内容总高 **805px**，且**与视口宽度无关**（行高、字号、项数都不随宽度变）：

| 组成 | 高度 |
|---|---|
| logo 行 | 64 |
| 数字员工（1 标题 + 7 项） | 285 |
| 资料库 + 能力（2 标题 + 9 项） | 395 |
| 账户条（sticky） | 61 |
| **合计** | **805** |

| 视口 | 可用高 | 余量 | 结论 |
|---|---|---|---|
| **iPad 横屏 1024×768** | 768 | **−37** | ← 就是这一档 |
| iPad 竖屏 768×1024 | 1024 | +219 | 本来放得下 |
| iPad Air 834×1112 | 1112 | +307 | 本来放得下 |
| 手机 390×844 | 844 | +39 | 理论够，但 Safari 地址栏还要再吃几十像素 |

### 「字体缩小」为什么无效

单把菜单字号 14 → 12，读数仍然是 805 ⇒ **省 0px**。

原因：`.sidebar-nav-menu .ant-menu-item { height: 34px; line-height: 34px }` 是写死的，
字号只决定字形大小，不决定行盒高度。缩字号的实际效果是「字更小、留白更多、一样要下滑」——
典型的**看着像修了、其实没修**。

### 另一个被顺带发现的现场问题

改前截图（`.workbuddy/probes/out/fit-pad-land.png` 旧版）里，「能力」组第二项
**「工具仓库」被 sticky 账户条压住**，只露出半行。

原因：内容 805 > 视口 768 ⇒ 账户条 `position: sticky; bottom: 0` 被提前提起 37px，
正好盖住最后一项。滚到底才能看见 —— 但滚动条是 `scrollbar-width: none`（第 260 轮老板要求「侧栏不出滚轮」），
所以没有任何「下面还有内容」的提示 ⇒ 观感就是「被截断了」。

内容压到 711 之后这一条自然消失（不再是覆盖关系）。

## 二、方案对比（收益全是注入真实样式量出来的，不是估的）

| 方案 | 省 | 压后总高 | 768 档 | 代价 |
|---|---|---|---|---|
| 只缩字号 14→12 | **0** | 805 | ✗ | 字更难读，等于没做 |
| 只压行高 34→30 | 64 | 741 | ✓ 余 27 | 触屏行高变小 |
| 只压标题 32→26 / 间距 8→4 | 30 | 775 | ✗ 差 7 | — |
| **行高 30 + 标题 28/间距 6 + 账户条 12** | **94** | **711** | ✓ **余 57** | 触屏行高 30px |
| 激进档（行高 28 + 字号 12） | 154 | 651 | ✓ | 字小 + 行更矮，可读性双降 |
| 「资料库」7 项折叠 | 245 | 560 | ✓ 余 208 | 每次找库多一次点击 |
| 三组全折叠 | 560 | 245 | ✓ | 信息全没了 |

老板在 r377 选了**「高度紧凑档」**（第 4 行）。
选它的理由：16 个入口零删减、一次到位、不需要为「找库」多点一次；
代价是触屏可点高度 34 → 30px（低于 iOS HIG 的 44 建议值），这是明确取舍，不是遗漏。

## 三、落地了什么（三处）

### 1. `frontend/src/config/layout.ts`
`VIEWPORT_BP` 增加第二个轴：

```ts
export const VIEWPORT_BP = {
  narrow: 1100,            // 宽度轴：摆不下三栏 ⇒ 换布局形态
  compactMaxHeight: 860,   // 高度轴：摆不下侧栏内容 ⇒ 压行高（本轮新增）
} as const
```

**为什么必须是高度轴**：这个缺陷与宽度无关。1280×720 的笔记本、带浏览器工具栏的 iPad，
宽度远超 1100，但高度一样不够 —— 只按宽度分档在那类设备上根本不触发。

**阈值 860 的来历**：805（内容）+ 55（余量）。
竖屏 iPad 1024 / Air 1112 不触发；横屏 768 / 720 笔记本 / 手机 844 触发。

### 2. `frontend/src/styles/sidebar-nav.css`（末尾）

```css
@media (max-height: 860px) {
  .sidebar-nav-menu .ant-menu-item { height: 30px; line-height: 30px; }
  .sidebar-section-title { height: 28px; margin-top: var(--space-6); }
}
```

字号**一个都没动**。

### 3. `frontend/src/components/Sidebar/AccountMenu.vue`（`</style>` 之前）

```css
@media (max-height: 860px) {
  .account-entry { padding: var(--space-4) var(--space-12); }
  .user-trigger  { padding: var(--space-4) var(--space-8); }
}
```

**位置很关键**：媒体查询**不提高优先级**，同选择器「后写的胜」。
第一版把它插在 `.user-trigger { padding: 6px 8px }` **之前** ⇒ 覆盖静默失效。
复核方式：读 `.account-entry` 的 computed `padding-top` 应为 4px。

## 五、门禁

### 静态：`check-sidebar-layout.cjs` 36 → **43 条**

| 编号 | 判什么 |
|---|---|
| S13a | `layout.ts` 声明了 `compactMaxHeight`（高度轴真源） |
| S13b | `sidebar-nav.css` 有 `@media (max-height: 860px)` 块 |
| S13c | 块内行高压到 30px |
| S13d | 块内标题压到 28px |
| S13e | `AccountMenu.vue` 用**同一个**阈值（这个数字两处硬编码，必须对齐） |
| S13f | 账户条纵向 padding 压到 `--space-4` |
| **S13g** | **紧凑档不许动 `font-size`** —— 守住「缩字号省 0px」这个实测结论 |

S13g 是这一组里最有价值的一条：它把「别再按直觉改字号」变成机器可执行的判据。

### 反向注入：`mutate-sidebar-compact.mjs` **7 处 · 7 抓到 · 0 逃逸**

| 变异 | 后果 |
|---|---|
| M1 阈值漂到 900 | 6 条红 |
| M2 行高改回 34 | S13c 红 |
| M3 标题改回 32 | S13d 红 |
| M4 账户阈值改 800 | 2 条红 |
| M5 账户 padding 退回 8px | S13f 红（**第一次逃逸过**，见下） |
| M6 加 `font-size: 12px` | S13g 红 |
| M7 媒体查询条件反转 | 4 条红 |

**M5 第一次逃逸，值得记**：原判据写成
`/\.account-entry\s*\{[\s\S]*?--space-4/`，
`[\s\S]*?` 越过了本规则的 `}`，在隔壁 `.user-trigger` 里找到了 `--space-4` ⇒ 条件恒真。
改成先用 `ruleBody()` 切出 `.account-entry` 自己的规则体再匹配，才真能红。

## 六、遗留

1. **极矮视口（< 711px）仍会滚动**，且滚动条隐藏（第 260 轮的既定要求）⇒
   那种高度下最后一项仍会被 sticky 账户条压住。要彻底解决得走「分组折叠」或「两段式」，
   本轮没做（老板选的是紧凑档）。
2. **触屏可点高度 30px** —— 低于 iOS 44 建议值。若后续有 iPad 误点反馈，
   最小改法是把紧凑档拆成两档（`max-height: 780px` 才压到 30，781–860 压到 32）。
3. 紧凑档只在 CDP 移动仿真里验过，没有实体 iPad 手测。
