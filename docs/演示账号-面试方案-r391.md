# 面试演示账号方案（r391）

> 起因：把项目挂在简历上供面试官自己登录；只有演示账号有数据，新注册账号进去是空的。
> 本文是双方口径的对账结果 —— 运维（网站管理员）出 4 件、项目侧出 3 件。
> 写完日期：r391

---

## 1. 结论：统一到一个真账号，但不碰「一键体验」哨兵

| 判断 | 结论 | 依据（实测） |
|---|---|---|
| 要不要统一到演示账号 | **要** | 线上 13 个用户里只有 1 个有数据；其余 11 个 0 店 |
| 用哪种机制 | **真凭据**（`POST /auth/login`） | 线上 `DEMO_MODE=false`，且前端 prod 构建 `VITE_DEMO_MODE=false` ⇒ 哨兵那一路已经不通 |
| 要不要修好「一键体验」 | **不要** | 它是往 localStorage 塞 `demo-token` 的伪登录；修好它＝让后端承认一个写在前端源码里的字符串，等于给鉴权开后门 |
| 新注册用户空工作区 | **降级为 P2** | 简历给了账号后，面试官自己注册的概率接近零；一句诚实话术 + 已有的「加载示例数据」按钮足够 |

**唯一有数据的账号**（线上）：`tenant-test-a@example.com`，4 家店
（亚马逊1 / 亚马逊2 / 虾皮1 / 虾皮2），数据量：
会话 1697 · 竞品快照 180×4 · 知识 FAQ 176 · 评价 23 · SPU 16。

## 2. 对运维方案的裁决

采纳四条主线（真账号 / A 案 / 不改 `ENVIRONMENT` / 预填代替伪登录），
但有三处需要修正，其中一处会**静默打断演示身份**。

### 2.1 采纳

| 他的判断 | 我方核实 |
|---|---|
| `account` 与 `user` 解耦，数据挂在 account id 上，改 email 不需要迁数据 | **成立**。可见性 = `accounts.owner_user_id` ∪ `account_members(ACTIVE)`；店铺只认 `account_id` |
| 改 `ENVIRONMENT=production` 会把站点搞挂 | **成立，我方原先的建议是错的**。护栏里 `PAYMENT_GATEWAY=mock` → 拒启；`stripe/wechat/paypal` → 未接实现拒启；`alipay` → 缺 4 项凭据或绝对回调地址就拒启；再加 `PASSWORD_HASH_ROUNDS>=12`、`METRICS_TOKEN`、`LOGIN_LOCKOUT_MINUTES>=5`。改了就是「配置改完 → 重启 → 8090 502」 |
| 锁定 5 次 / 15 分钟，且是「先判锁再判密码」 | **成立**。`login_max_failures=5`、`login_lockout_minutes=15`，锁定期内密码正确也返回 429 |
| 用「填入演示账号」链接代替伪登录 | **采纳**（本批已实现，见 §3.2） |
| 靠清零 `failed_login_count` 而不是给演示账号开豁免 | **采纳**。豁免=降低防护，清零是运维动作，方向正确 |

### 2.2 修正一：A 案**不要改 email**（这是他能算漏代价的地方）

他写「A 案 = 一条 UPDATE 改 name / email / hashed_password，数据零迁移」。
数据确实零迁移，但 **email 是 4 处字面量的真源**：

| 位置 | 内容 |
|---|---|
| `backend/tests/test_demo_store.py` | `DEMO_ACCOUNT_EMAIL = "tenant-test-a@example.com"`，且 `DEMO_SHOP_IDS` 里钉了 4 个 store id |
| `backend/core/config.py` | `demo_account_email` 的**声明默认值** |
| `backend/scripts/check_tenant_isolation.py` | `ensure_user("tenant-test-a@example.com")` —— email 一改，它会**新建一个空用户**，隔离测试的被测夹具就没了 |
| `backend/scripts/backfill_owner_id.py` | `TARGET_EMAIL` |

⇒ **本批结论：只改 `name` + `hashed_password`，email 不动。**
简历上写「演示账号：tenant-test-a@example.com」不丢人（它本来就是演示账号），
换好看邮箱是**面试后的整理项**，不值得在面试前动地基。

### 2.3 修正二：这个坑必须写下来 —— `is_demo` 是**双向收敛**的

他的方案里有一句「4 家店的 `is_demo` 也不会丢」。在「原地改 email」这一前提下成立，
但如果为了好看的邮箱改成「新建 user + 加一条 `account_members`」（他的解耦论证很容易
把人引到这条更干净的路上），后果是：

```
ensure_demo_stores():  want = (store.account_id == demo_account_id())
                       demo_account_id() = 「该 email **拥有**的 account」
```

新账号只是**成员**不是 **owner** ⇒ `demo_account_id()` 返回新账号自己的 account
⇒ 4 家店的 `want` 全变 False ⇒ **下一次启动被打回 `is_demo=False`**。
而数据完好、接口全 200，现象只是「演示少了 4 家店」。

⇒ 结论：**任何情况下都不要用「新账号 + 成员身份」替换演示账号。**
真要换，只有两条路：原地改 email（并同步上表 4 处），或改 `accounts.owner_user_id`。

### 2.4 修正三：「禁删号」没有对应端点

全仓 `DELETE` 端点只有：`/stores/{store_id}`、`/accounts/{id}/members/{id}`、
`/api-keys/{key_id}`。**没有注销用户/删除账户的端点** ⇒ 这一条删掉，别写进清单装样子。

真正需要保护的写路径是三条（本批全部已拦）：

| 路径 | 不拦会怎样 |
|---|---|
| `POST /auth/change-password` | 公开口令 ⇒ 公开修改权 ⇒ 一个人手滑改掉，后面所有人登不进（那个 email 收不到重置信） |
| `DELETE /stores/{id}` | 演示少一家店，物理删除、无恢复路径 |
| `POST /stores/{id}/transfer` | **最隐蔽**：不删数据，但店一转移，下次启动 `is_demo` 被打回 ⇒ 演示看不到它 |

## 3. 项目侧（本批已完成）

### 3.1 演示账号写保护

- 判定唯一真源：`core/auth/demo_identity.py::is_demo_account(user)`
  —— 按**身份**（`email == config.demo_account_email`，大小写/空白归一）判，
  与哨兵（`is_demo_request`）是两件事。配置为空 ⇒ False（只加限制，不误伤）。
- 三处拦截：改密 / 删店 / 转移店铺，全部返回 **403**，文案说明「请注册自己的账号」。
- 门禁：`backend/tests/test_demo_account_protection.py`（10 条）。
  **双向**：既测「演示账号被拦」，也测「真实账号不受影响（仍走原来的 400/404）」。
- 反向注入 **5/5 HIT**：拆改密守卫 / 拆删店守卫 / 拆转移守卫 /
  判定恒 False（放开）/ 判定恒 True（误伤）。按字节还原 + sha256 + 复跑回绿。

### 3.2 登录页「填入演示账号」

- `frontend/src/config/demoAccountHint.ts` + `Login.vue`：点一下把 email/口令
  **预填**进表单，用户仍点**真正的登录按钮**（走 `/auth/login`）。
  不自动提交、不写 localStorage、不产生任何凭据状态。
- 由 `VITE_DEMO_HINT_EMAIL` / `VITE_DEMO_HINT_PASSWORD` 控制，**留空 = 整段不渲染**（当前留空）。
- 门禁 `check-prod-demo-flag.cjs` 增 H1~H4（已挂进 `npm run build`，实测 4 条全红、对照组绿）：
  - **H1** 两个值必须成对（半配 = 配了却不渲染的静默失效）
  - **H2** 与 `VITE_DEMO_MODE=true` 互斥（伪登录 vs 真凭据，语义相反）
  - **H3** 口令不得含 `0/O/1/l/I`（现场手打会看错，失败现象与"口令错了"无法区分）
  - **H4** email 形态合法

### 3.3 一个必须说清的后果

`VITE_DEMO_HINT_*` 是**编译进产物**的 ⇒ 口令对任何打开页面的人可见。
面试场景下这是有意的（凭据本来就写在简历上），但由此得到两条硬约束：

1. 这个账号**不能**同时是任何真实用户的账号（已按身份加写保护）；
2. **轮换口令 = 必须同批重建产物 + 重新部署。** 只改库不重建，旧产物会预填
   旧口令 ⇒ 面试官点一下、点登录、看到「邮箱或密码错误」⇒ 比不填更糟。

### 口令轮换命令（运维执行；项目侧不改线上库）

```bash
# 1) 生成 bcrypt（口令用参数传入，不写进 shell 历史）
cd /opt/ecommerce/backend
.venv/bin/python -c "import sys; from core.identity.router import hash_password; print(hash_password(sys.argv[1]))" '<NEW_PASSWORD>'

# 2) 只改 name + 口令，email 不动（见 §2.2）
sudo -u postgres psql -d ecommerce -c \
  "UPDATE users SET name='演示账号', hashed_password='<上一步输出>' WHERE email='tenant-test-a@example.com';"

# 3) 确认改动只落在一行上
sudo -u postgres psql -d ecommerce -tAc \
  "SELECT email, name, left(hashed_password,7) FROM users WHERE email='tenant-test-a@example.com';"
```

⚠️ 口令一旦轮换，**同一批**必须：把两个值写进 `frontend/.env.production.local`
（gitignored，**不进仓库**）→ `npm run build` → `deploy_ecommerce.py --only-fe`。

> 为什么不写进 `.env.production`：它会被 commit，而口令一旦入库就永久留在
> 历史里（轮换也删不掉），且本来就会被编译进产物对所有人可见 ——
> 没有任何理由再让它多一份仓库副本。构建门禁 H1~H4 照样生效：
> `check-prod-demo-flag.cjs` 会把 `.env.production.local` 与另外两份一起合并读取。

**口令形态建议**（运维提的，采纳）：12 位、纯字母数字、不含 `0/O/1/l/I`、不含特殊符号。
现场手打可读性 > 熵。

## 6. 明确不做的

| 项 | 理由 |
|---|---|
| 修「一键体验」哨兵 | 等于给鉴权开免认证后门（见 §1） |
| 改 `ENVIRONMENT=production` | 会把站点搞挂；改用外部巡检守卫（见 §4.3） |
| 给演示账号开登录锁定豁免 | 降低防护；靠「清零 + 预填」解决（见 §2.1） |
| 新注册用户灌同一套数据 | 两份不同质量的数据集反而更困惑；一句诚实话术 + 已有「加载示例数据」按钮 |
| 换好看的 email | 4 处字面量的真源要同步，面试前不动地基（见 §2.2） |

## 7. 上线执行顺序（给运维的一页纸）

§5 的判据分两层：**代码层我已自测**（本机跑门禁即得），**线上层只能等你部署完才能验**。
下面按「谁做 / 什么时候做」重排，含两个会让结果看起来像失败的坑。

### 7.1 顺序不能反

| 步 | 动作 | 谁 | 做完的判据 |
|---|---|---|---|
| 1 | 部署本批代码（后端 + 前端产物） | 运维 | `/version.json` 的 commit 含 `2e122b8` |
| 2 | `.env` 补 `DEMO_ACCOUNT_EMAIL=tenant-test-a@example.com` | 运维 | 重启后 `GET /openapi.json` 正常、登录 200 |
| 3 | 清零 `failed_login_count` / `locked_until` | 运维 | 上表 §5「演示账号登得进」= 200 |
| 4 | 定口令 → 写 `frontend/.env.production.local` → **重建** → 再发前端 | 运维 + 我方 | 登录页出现「填入演示账号」，点一下表单有值 |
| 5 | 跑 §5 的四个 403 判据 | 运维 | 改密/删店/转移全 403，真实账号不受影响 |

★ **第 4 步现在不配也完全能用**：`VITE_DEMO_HINT_EMAIL/PASSWORD` 当前**留空** ⇒
登录页**整段不渲染**、一行代码不执行。想先让面试官手打，就跳过第 4 步，其余全部有效。

### 7.2 两个坑（都会让「做对了」看起来像「没生效」）

1. **只改库不重建 = 预填的旧口令**。`VITE_DEMO_HINT_PASSWORD` 是**编译期**常量，
   `vite build` 时被静态写进 bundle。改库不重建 ⇒ 面试官点一下、点登录、
   得到「邮箱或密码错误」—— 比不填更糟。**轮换口令必须同批重建 + 重发 `dist/`。**
2. **前端产物与后端不必同批，但这次的写保护必须后端先上**。顺序反了（前端先有预填、
   后端还没 403 守卫）不会报错，只是演示账号在那段时间里**可被改密/删店**。
3. 判「预填生效了」别只看页面：产物里搜得到 email 才算编译进去 ——
   `grep -c 'tenant-test-a@example.com' dist/assets/index-*.js` ≥ 1。
