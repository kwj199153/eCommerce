# 法务文本目录（P0-9 · 草稿）

> **⚠️ 本目录下的全部文本均为「工程侧草稿模板」，不是法律文书，也不是法律意见。**
> 上线前**必须**由具备资质的执业律师/法务按实际经营主体、实际数据处理事实审阅并定稿。
> 本目录的价值在于：把"从零起草"降级为"填空 + 审阅"，并把**需要业务方拍板的字段**
> 显式暴露成占位符（见 [`PLACEHOLDERS.md`](./PLACEHOLDERS.md)）。

## 为什么会有这一组文件（P0-9 的由来）

技术尽调（`docs/technical-diligence-review-20260930.md`）的第 9 项 P0：
全仓 **LICENSE / 隐私政策 / 服务条款 零命中**。这在一个**多租户 SaaS**
（承载店铺授权凭据、订单、买家差评、账单）上属于硬缺口：

- 没有**服务条款** ⇒ 与付费客户之间缺少责任边界、可用性承诺、终止与退款规则的书面约定；
- 没有**隐私政策** ⇒ 收集了个人数据（账号邮箱、登录 IP、对话内容、上传素材）
  却没有履行告知义务，**本身即构成合规风险**（《个人信息保护法》第 17 条）；
- 没有**数据处理协议（DPA）** ⇒ 面向企业客户（他们可能把自身客户的个人信息
  一并带进本平台）时，无法回应其"你是受托处理者吗、怎么保障"的尽职调查；
- 没有 **LICENSE** ⇒ 源代码的权利状态默认不明（"保留所有权利"需要**明示**才清晰）。

## 法务审阅提示（交给律师时一并转达）

审阅时请特别确认以下几处**与产品实际行为绑定**的表述是否成立（它们最容易"写得比做得多"）：

1. **个人信息的范围与来源**。本平台同时处理三类个人数据，来源与角色都不同：
   - *我们自己收集的*：账号邮箱、密码哈希、登录尝试（IP / 时间）、审计日志、对话内容、上传素材；
   - *客户带入的*：店铺授权凭据、**买家评价正文**（可能含个人数据）、订单收货信息（取决于客户是否同步）；
   - *第三方生成的*：LLM 输出、AIGC 图片、语音合成音频。
   ⇒ 需确认：我们分别处于"个人信息处理者"还是"受托处理者"地位，以及告知/同意链条如何衔接。
2. **第三方与子处理者清单**是否完整、准确（当前实现至少涉及：阿里云百炼 DashScope
   〔LLM / 嵌入 / 文生图 / 语音合成〕、Amazon SP-API、Shopee Open Platform、
   支付宝、邮件发送通道、对象存储）。**清单必须与代码里真实调用的服务逐一比对**，
   漏一个就是未披露的对外提供。
3. **跨境传输**：若选用境外模型或境外存储，需明确传输路径与合法性基础
   （标准合同 / 安全评估 / 认证之一），并在隐私政策中单列。
4. **数据留存期与实际行为是否一致**：本仓已有可配置的保留期
   （`audit_retention_days` / `login_attempt_retention_days` / `email_token_retention_days`）
   与定时清理任务。政策里写的天数**必须**与这些配置的**生产取值**一致，
   否则构成"承诺比实际做得久"的虚假陈述。
5. **AI 生成内容**的责任分配与免责边界（尤其面向 Amazon/Shopee 的商品文案——
   平台规则下的违规责任归属于谁）。
6. **未成年人**条款是否需要（B2B 场景通常以"不面向未成年人"表述为妥）。
7. **LICENSE 的形态**：当前默认**专有**。若项目定位为开源，应整体替换为对应许可证
   （MIT / Apache-2.0 / AGPL 等），并**同步**处理前端 bundle、Docker 镜像的声明要求；
   不要"专有许可 + 仓库却是公开的"这种自相矛盾状态。

## 维护约定

- 占位符统一写作**双花括号包裹的大写下划线名**（例如把字段名 `COMPANY_LEGAL_NAME`
  用双花括号包起来），**只允许**出现在本目录；新增字段必须同步登记进
  `PLACEHOLDERS.md`，否则视为"漏填项"。
- 定稿后不要删占位符文件——它是"下一份合同/下一个客户"复用同一套模板的锚点。
- 每次**产品或数据处理行为**发生变化（新增数据类别 / 新增第三方 / 改变留存期 /
  新增跨境），都应回到本目录核对并更新对应条款（这是合规文本失效的最常见路径）。
