## 〇、先报三条实测（我拿到的是线上现场，不是推断）

### 1. 6380 从来不存在 —— 「共用」不是设计，是 edu 的 example 没落地

```
$ ss -lntp | grep -E ':(6379|6380)\b'
LISTEN 127.0.0.1:6379   "redis-server",pid=3147726     ← 只有一个进程，Oct15 起
[::1]:6379              "redis-server",pid=3147726

$ redis-cli -p 6380 info keyspace
Could not connect to Redis at 127.0.0.1:6380: Connection refused

$ grep '^REDIS_URL=' /opt/eeducation/backend/.env.example   →  redis://127.0.0.1:6380/0
$ grep '^REDIS_URL=' /opt/eeducation/backend/.env           →  redis://localhost:6379/0
```

两站共用 6379 是**既成事实**（机器上就一个实例），但它不是设计出来的：
eEducation 仓的真源写着 **6380**，线上写 **6379**，端口还差一个 `localhost` vs `127.0.0.1`。

**为什么没被发现**：你方 `_scratch/_chk_env_isolation.py` 的端口清单是
`:(8001|8002|5432|6379)` —— 里面没有 6380。所以脚本只会回答「两站都在 6379」，
而不会问「edu 本该在 6380，那个实例哪去了」。

**这条影响你方结论的前提，不是影响我们的取值**：
- 若认定 edu 就该在 6379 ⇒ 请把 edu 的 `.env.example` 改成 6379（它现在的真源是错的，比线上错得更久）
- 若 edu 该有独立实例 ⇒ 起 6380，两站物理隔离，我们的 db3 依然无害（只是隔了空库）

**建议先定这一条再登记分库表**，否则表里的 edu 那一格填 6379 还是 6380 没有依据。

### 2. 你方一处事实错误：缺 `CELERY_*` 不会落 db0，会落 /1、/2

你方写「线上 `.env` 缺这两行 → Celery 启用前必须补，否则会默认落到 db0」。实测我方代码：

```python
# backend/core/config.py:414-415（声明默认值，env 缺失时生效）
celery_broker_url:     str = Field(default="redis://127.0.0.1:6379/1", ...)

```

⇒ 不配 env 也只会落 /1、/2，不会落 /0。**「补这两行」仍然要做**（否则线上与 example 不一致，
下一个人照 example 又装一遍），但理由不是「防落 db0」。
（这条我顺手钉成了门禁 D2：`.env.example` 与 `config.py` 默认值分叉也报红。）

### 3. 「等 31 小时让键自然过期」可以不等 —— 直接迁移，代价为零

```
$ redis-cli -n 0 --scan   →  auth:revoked:jti:<hash>   len=49
$ redis-cli -n 0 ttl  <k> →  108633        # ≈30.2h，你方说的 31h 是对的
$ redis-cli -n 0 type <k> →  string   vlen=1
```

⚠️ 但**不要用 `info keyspace` 的 `avg_ttl` 判 TTL**：它显示 `108637550`（≈3.4 年），
是采样估算噪声。我一开始差点据此断言「要等 3.5 年」，读到单键 TTL 才发现是自己错。
判据只认 `TTL <key>`。

既然只有 **1 个键**、值就一个 `"1"`，迁移成本可忽略（见 §二 第 1 步）。
不用等一天，也不会有「已撤销 token 在窗口内复活」的降级。

## 二、上线步骤（可直接执行）

```bash
# ── 1 先迁移 db0 的唯一键（值 + 剩余 TTL），再切库 ──────────────
k=$(redis-cli -n 0 --scan --pattern 'auth:revoked:jti:*' | head -1)
if [ -n "$k" ]; then
  v=$(redis-cli -n 0 get "$k"); t=$(redis-cli -n 0 ttl "$k")
  redis-cli -n 3 setex "$k" "$t" "$v"
  echo "migrated $k ttl=$t"
fi

# ── 2 改线上 .env（只改自己那一方，.env.example 已在仓里改好）────
sed -i 's#^REDIS_URL=redis://127.0.0.1:6379/0$#REDIS_URL=redis://127.0.0.1:6379/3#' \
  /opt/ecommerce/backend/.env
grep -q '^CELERY_BROKER_URL=' /opt/ecommerce/backend/.env || printf \
  'CELERY_BROKER_URL=redis://127.0.0.1:6379/1\nCELERY_RESULT_BACKEND=redis://127.0.0.1:6379/2\n' \
  >> /opt/ecommerce/backend/.env

# ── 3 重启 + 验收 ────────────────────────────────────────────
systemctl restart ecommerce
```

### 验收判据（你方 4 条我改了 2 条，理由附后）

| # | 命令 | 期望 |
|---|---|---|
| 1 | `curl -s -o /dev/null -w '%{http_code}' .../api/v1/health` | `200` |
| 2 | 登录一次后 `redis-cli -n 3 dbsize` | **> 0** |
| 3 | `redis-cli -n 0 dbsize` | **0**（不是「保持 1」） |
| 4 | `redis-cli -n 3 --scan --pattern 'auth:revoked:*' \| wc -l` | == 迁移前条数（本轮=1） |
| 5 | `redis-cli -n 1 dbsize`、`redis-cli -n 2 dbsize` | 仍 0（Celery 未部署，不该有东西） |

**改判据的理由**：你方 #3 写「旧库保持 1 且 TTL 递减」是**基于「等它自然过期」的方案**。
我们改成迁移 ⇒ 迁移完成后 db0 就该是 **0**。若仍按「保持 1」验，会把成功读成失败。
判据要跟着方案走 —— 这是本仓踩过的「期望值过期伪装成真回归」。

## 三、对你方方案的两处口径修正

### 1. 「分库表写进 `.env.example`」与你方刚立的「真源归属法」冲突

你方规则原文：「跨项目的真源不属于任何项目仓 ⇒ 归运维」。
分库表横跨 edu / eco / celery 三方，它**不是任何一个项目仓的真源**。
写进我们仓的 `.env.example` 会变成：eco 仓里存着 edu 的库号，下一个照抄的人分不清
「这是真源」还是「这是别人抄过来的副本」—— 正是你方要防的那种不一致。

**建议**：分配表放你方 `shared/`（一处登记），我们仓只声明「本项目占 3」并在注释里指向它。
我们已按这个写法落了注释（`★ 实例级分配表归运维登记；本文件只声明本项目占 3`）。
若你方那份表还没建，我们这份注释就是临时真源，建好后指过去即可。

### 2. 「两站挤 db0 会串」——我核过，**当下不会串**（你的定级是对的）

| 站 | 限流键格式 | jti 黑名单 |
|---|---|---|
| eCommerce | `ratelimit:{bucket}:{ip}` | `auth:revoked:jti:<jti>` |
| eEducation | `rl:{bucket}:{kind}:{who}:{window}` | 无（它走 token_version） |

格式不同 ⇒ 两站在同一个库也不会互相 incr 同一个键。你方「潜在风险、非当下故障」的定级准确。

**但** `auth:revoked:jti:` 这个前缀**没有站点标识**：edu 若将来也上 jti 黑名单，
两边就共用一个命名空间。分库这件事本身就消掉了这个隐患 ——
这是我们做它的**第二个**理由（第一个是给 Celery 的 1/2 让路）。

## 五、一条不属于本轮、但建议排期的事

**Redis 是撤销名单的唯一存储，且它是无配置启动的**：

```
$ ps -ef | grep '[r]edis-server'
redis 3147726 1 0 Oct15 /usr/bin/redis-server 127.0.0.1:6379      ← 没有 config 参数
```

默认配置下 RDB 快照可能丢最后一段写入；**redis 重启 = 已登出的 token 全部复活**，
且不会有任何报错。分库不改变这一点（只是把风险搬到 db3）。

真修法二选一：
- 短 TTL access token + refresh 白名单（黑名单失效窗口天然很小）
- 或把 `jti` 撤销表落 PG（与 `aigc_jobs` 同一思路：状态权威源在库不在缓存）

这条不阻塞 P2-1，先记在这里。
