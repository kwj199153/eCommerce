## 3. P1-3 = L3-5：OpenAPI 契约快照

### 3.1 交付物

| 文件 | 说明 |
|---|---|
| `backend/scripts/check_openapi_contract.py`（430 行） | 门禁本体。判据**全部住在这里**，用例只断言退出码与关键行 |
| `backend/docs/api/openapi.json` | 快照，**236 路径 / 151 schema / 592832 B（≈579 KiB）**。★ **它本身就是交付物** —— 前端/第三方要接 API 直接读它，不必起服务 |
| `backend/tests/test_openapi_contract_gate.py`（**8 条**） | 进 CI 的包装（`ci.yml` 的后端 job 跑 `pytest tests/ -q` ⇒ 自动纳入，无需新增 workflow 步骤） |

退出码三档分开：**0** = 一致；**1** = 漂移；**2** = 环境/脚本自身的错
（快照缺失或损坏、app 导不进来、路径数低于健全性下限 200）。
★ 为什么必须把「缺失(2)」与「漂移(1)」分开：快照缺失时**无法**判断契约对不对，
若共用退出码或返回 0，「有人删掉快照」就会表现成「契约是好的」。

### 3.2 ★ 本轮最值钱的实测：契约的环境敏感轴只有**一根**

固定环境让契约确定可复现（CI 无 `.env`、本地有 ⇒ 不固定就会「一处恒绿、另一处恒红」），
**代价是其它 env 轴的影响会隐身**。所以先把轴逐条实测清楚：

| env | 对契约的影响 | 处置 |
|---|---|---|
| `VOICE_CLONE_ENABLED` | **有**：off 少 **8** 条 `/api/v1/voice-clone*` 路径、少 **5** 个 schema（236→228 / 151→146） | 固定 `true` ⇒ 快照取**最大面**；差异面由 `--env-axes` 单独钉住 |
| `AUTH_REQUIRED` | 无 | 固定，且由 `--env-axes` 钉住（见下） |
| `DEBUG` | 无 | 只影响 `/docs` `/redoc` 挂不挂 —— 二者**不在 schema 的 paths 里** |
| `METRICS_ENABLED` | 无 | `/metrics` 是 `include_in_schema=False`（`main.py`）⇒ **天然不入册** |
| `DEMO_MODE` | 无 | 演示是**请求期**行为 |
| `ENVIRONMENT` | **测不了** | `production` 下 `import main` 被 `_enforce_production_safety` 拦下（缺 `METRICS_TOKEN` 即拒启）⇒ 门禁固定 `development` |

★★ **踩过的坑（写下来防再犯）**：第一版矩阵只写了 `VOICE_CLONE_ENABLED=true`，
结果**五组 env 的 sha 完全一致**，差点得出「契约与环境无关」的**反向结论**。
真因是本地 `.env` 里它已经是 `true` ⇒ **等于没切换**。
⇒ 测 env 轴时**必须显式关掉**才算测过另一侧。

### 3.3 `--env-axes`：为什么它不是「顺手多测一下」

上表「无影响」那几行如果**将来不再成立**，固定环境会让它**永久隐身**：
例如有人再加一个 `if config.X: include_router(...)`，生产真实提供的契约与快照不同，
而正向门禁**全绿** —— 本仓 2026-09-17 前正是这个缺陷形态
（`BUSINESS_AUTH = [Depends(...)] if config.auth_required else []`）。

`--env-axes` 用**子进程**把两根轴各翻一次，断言：

- `AUTH_REQUIRED` ⇒ 契约**逐字节不变**；
- `VOICE_CLONE_ENABLED` ⇒ 差集**恰好**是 voice-clone 前缀下的路径，**且差集非空**
  （否则「voice-clone 被整个删掉」会让这条「差集为空 ⇒ 恒真」地假绿）。

实跑：`✔ AUTH_REQUIRED=true → false：契约逐字节不变`、
`✔ VOICE_CLONE_ENABLED=true → false：恰好少 8 条`。

### 3.4 反向注入当场抓出门禁自身的 bug

`diff(old, text)` 里传了**规范化字符串**而不是 dict ⇒ `AttributeError: 'str' object has no attribute 'get'`，
门禁**直接崩**（`--check` 漂移时必崩，而这个分支正是它唯一的用处）。
由反向用例抓到并修掉。
★ 这是「**判据本身也是被测对象**」的又一例：正向用例（当前树与快照一致）永远走不到 diff 分支。

### 10.1 L3-5 门禁「在 CI 里从未实跑」→ 已实跑（并发现真 bug）

做法：`git worktree add --detach <tmp> HEAD` 建一份**干净检出** ——
`.env` 被 gitignore ⇒ 检出里天然没有它，这就是 CI 的等价条件。
（比 `mv .env` 安全：不动本机运行中的 uvicorn，也不依赖 CWD 解析。）

**结果 rc=1：门禁在 CI 上会红。** 漂移面只有一处：

| | `info.title` |
|---|---|
| 快照（本地有 `.env`） | `CrossBorder-AI-SaaS` |
| 无 `.env`（= CI） | `跨境电商AI SaaS` |

根因：`main.py:153` 的 `FastAPI(title=config.app_name, version=config.app_version, ...)`
把两个 config 字段**直接写进 `info`** ⇒ 它们是**第二根 env 敏感轴**。
上一轮的矩阵只比了「有 `.env`」那一档，而 `.env` 恰好把 `APP_NAME` 改成了非默认值
⇒ 整条轴隐身，连带 docstring 里「只有一根轴」的结论一起失效。

★ 与 r353 的 L3-17 同族但更隐蔽：那次是「**门禁红了没人看**」，
这次是「**门禁在本地永远绿、只在 CI 红**」—— 两者都源于「只在一处验证过」。

修复（`20d0b1c`）：
- `FORCED_ENV` 补 `APP_NAME` / `APP_VERSION`（取值 = `.env.example` = 代码默认；
  `docker-compose.yml` 未设 `APP_NAME`）；快照随之重生成，差异**恰好 1 行**
- `--env-axes` 新增**轴 3**：覆写 `APP_NAME` 后差异必须**恰好**是 `info` 一项、且 title 跟着走
- docstring 的轴表补两行，并注明原结论已被证伪

复验（同一份 worktree + CI 的 `env:` 段：`DATABASE_URL`/`REDIS_URL`/`AUTH_REQUIRED=false`…）：

### 10.2 生产 env 的契约 → 静态取证回答，并钉成门禁

`ENVIRONMENT=production` 起不来是**设计**（`_enforce_production_safety` 拒启），
它拦的是实收钱 / 发信 / 弱口令这类**业务配置**，都不进 OpenAPI schema。
而 schema 的差异面只有「条件挂载」，于是改用**静态取证**：

`main.py` 里按 config 字段条件挂载路由的地方**只有一处** ——
`if config.voice_clone_enabled: app.include_router(voice_clone_router, ...)`；
`metrics_enabled` 那块只有 `include_in_schema=False` 的 `/metrics`（天然不入册）；
`docs_url`/`redoc_url` 不是 schema 的一部分；`BUSINESS_AUTH` 自 2026-09-17 起是**无条件常量**。

⇒ 生产 env 不产生额外差异，且该轴已被轴 2 翻转钉住。

★ 但「今天只有一根轴」≠「明天还是」：`--env-axes` **只翻已登记的轴**，
所以「新加一根轴」它天然看不见（它翻的两根照样符合预期、退出码 0）。
补两条用例堵死这层：

| 用例（8 → 10 条） | 守什么 |
|---|---|

| `test_registered_axes_are_actually_flipped` | 登记表里的轴必须真的被 `--env-axes` 翻过（防「登记了不翻」） |

登记表 `_CONDITIONAL_MOUNT_AXES = {"voice_clone_enabled"}` 就住在测试文件里；
新增轴时**指名道姓**报红，并给两条修法（固定进 `FORCED_ENV` / 补一条翻转断言）。

### 10.7 收尾时被门禁抓到的第 4 件事：扫描面吃了自己的 basetemp

§10.1 ~ §10.3 之外，收尾跑门禁时又冒出**一条红，且红的原因不在业务代码**：

```
FAILED tests/test_no_syntax_warnings.py::test_no_syntax_warnings_across_backend
  .pytest-tmp-r354c\test_gate_detects_injected_war0\injected_bad_escape.py:1:

```

`injected_bad_escape.py` 是 `test_gate_detects_injected_warning` 用 `tmp_path`
**故意**造的坏文件（它是反向注入的夹具）。它落进了 `backend/.pytest-tmp-r354c/`
（= 我把 `--basetemp` 指在了被测树内），于是被同文件的 `_iter_sources()` 扫到
⇒ **门禁被自己的元测试产物打红（自伤假红）**。

**不是手滑**：`backend/.gitignore` 第 25–29 行明文约定 basetemp 必须落在 `backend/` 内 ——
因为 `atexit` 清 `%TEMP%/pytest-of-*/garbage-*` 会撞沙箱批量删除守卫，且**跑完之后**才抛。
⇒ 推论：**凡「以 `backend/` 为根扫 `*.py`」的判据，天然会被自己的临时产物污染。**

实测底盘：

|---|---|

★ 也就是说：**「门禁的门禁」只堵了 vendored 一半**（`.venv` / `site-packages`），
`.pytest-tmp*` 这一半敞着 —— 而后者比前者更隐蔽：它是**项目自己造的**、**每轮都在产生**。

## 11. A 方案落地：16 个扫描器一次扫平 + 门禁扩双轴（第 4 件 · 根治）

§10.7 只修了**实际受害的那 1 个**文件，另 16 个同缺陷类的扫描器敞着。本节是根治。

### 11.1 修法：一律改成**前缀式**判定

16 个文件的既有排除形态并不统一（集合交集 / 精确成员 / 子串 / 生成器内嵌），
逐处对账后统一追加**前缀式**判定：

    or any(part.startswith(".pytest-tmp") for part in ...)

★ 为什么**不能**图省事塞进现成的 `{".venv", "venv"} & set(parts)`：
那是**精确匹配**，而 basetemp 实际叫 `.pytest-tmp-r354c` —— **匹配不到**。
（`.venv` 用精确匹配是对的：目录名就叫 `.venv`。basetemp 带后缀，只能用前缀。）

| 原形态 | 文件数 | 改法 |
|---|---|---|
| `{...} & set(parts)` 集合交集 | 5 | 追加 `or any(...startswith...)` |
| `any(part in SKIP for part in X)` | 8 | 在生成器里内嵌 `or part.startswith(...)` |
| `A or any(s in rel ...)` 子串式 | 2 | 追加 `or any(...startswith...)` |
| `"..." in rel` 子串式 | 1（2 处） | 追加 `or any(...startswith...)` |

合计 **16 个文件 / 20 个操作点**（`test_context_propagation.py` 的同一段代码出现
2 次，一次 `replace` 覆盖两处）。门禁本体另有 **4 处**改动（见 11.2）。

★ 锚点纪律：改前先实测「锚点确实存在」（`old` 命中数 == 期望），否则
`.replace()` 会**静默空跑**。20 个操作点在预演时全部命中，无未命中。

### 11.2 门禁扩轴：vendored 单轴 → 双轴

`backend/tests/test_ci_gate_coverage.py` 改 4 处：

1. 顶部注释：补第二根轴的成因（本仓 basetemp 必在 `backend/` 内）与**判据 5**；
2. 抽出 `_iter_backend_root_scanners()`：两条用例**共用**同一份遍历
   （本仓铁律：同一判定禁两份实现）；
3. 新增 `_basetemp_excluded(tree)`：AST 判「存在 `X.startswith(...)`，且实参
   （字面量 / 元组内嵌 / **模块级常量名**）含 `.pytest-tmp`」；
4. 新增用例 `test_backend_scanning_gates_exclude_pytest_basetemp`。

★ 判据刻意**不认**「把 `.pytest-tmp` 塞进集合」的写法 —— 那正是本次缺陷的
伪装形态（看着像修好了，实则对带后缀的目录名无效）。反向注入 I2 专验这一条。

### 11.5 教训

**「修受害者」≠「修缺陷类」。** §10.7 修完后我写「另 16 个今天不匹配污染内容，
所以不红」—— 这句是**对现象的正确描述、对风险的危险辩护**：污染内容由
**谁往 basetemp 里写什么**决定，而那是**门禁自己的元测试**，下一轮改一个断言
就会换一份内容。今天恰好只有 1 个扫描器的模式撞上，是运气。

⇒ 判据的**读集**要按「最小可信集」定义（哪些目录**永远不该读**），
而不是按「今天谁受害」定义。
