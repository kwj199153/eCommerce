## 2. 反向注入：门禁到底有没有牙齿（原则二 / 判定三问第 2 问）

### 2.1 做法（**零副作用**）

把每道门禁的「读取根」用其**自带的 env 注入钩子**指向一个**空目录 / 空文件**，
**一个字节都不改真实源码**。判据：**读取源全空 ⇒ 门禁必须红**。

### 2.2 结果

| 类别 | 数量 | 结论 |
|---|---:|---|
| **RED ✔**（指向空源后变红） | **38** | 有牙齿的最低门槛通过 —— 无一道恒真 |
| **GREEN ✘**（空源仍绿 = fail-open） | **0** | **未发现 fail-open 门禁** |
| **NO-HOOK**（无 env 注入开口） | **1** | `check-eslint-ratchet.cjs` —— 读的是 **ESLint 配置面**、不读源码 ⇒ **非缺口** |

⇒ 与 `review-principles.md` §5 快照记载（「注入开口 38 道 / 无开口 1 道」）**逐字吻合**。

### 2.3 ★★ 方法论收获：**探针口径过期，会给出完全相反的结论**

本轮首跑（复用 r350 的探针）得到的是 **RED 26 / GREEN 0 / NO-HOOK 13** ——
按那个数会得出「**r351 声称补的 8 道注入开口没落地**」的结论，**与事实相反**。

**根因**：r350 的探针只用一条正则识别钩子：

```python
re.findall(r"process\.env\.([A-Z0-9_]+)", src)          # 只认「点号 + 字面量名」
```

而 r351 起新补的开口写成**动态键**：

```js
const pick = (env, fallback) => process.env[env] ? path.resolve(process.env[env]) : fallback
const FE = pick('SORT_FE_ROOT', path.resolve(__dirname, '..'))   // ← 方括号 + 变量，对点号正则「隐形」
```

⇒ 8 道**已有开口**的门禁被判成 NO-HOOK。修正判据（同时认 `process.env.LITERAL` 与 `pick('NAME')`）后重跑：
**RED 38 / GREEN 0 / NO-HOOK 1**（即 §2.2）。

★ **教训（与「门禁的读集变了 ⇒ 注入台架的副本树必须跟着复制」同源）**：
**注入探针的「钩子识别口径」必须跟着门禁写法一起演进**，否则会把「换了写法的开口」
静默归零成「没有开口」。这类错误**方向是危险的**：它把「已做」报成「未做」，
会诱发**重复劳动**，而不是遗漏。

## 3. ★ 本轮最重要发现：一道「红着也没人知道」的门禁

### 3.1 现象

```
$ cd backend && ./.venv/Scripts/python.exe scripts/check_tenant_isolation.py
AUTH_REQUIRED = False
用例：
  [FAIL] 演示模式：无 token 也放行（保证演示可用）: 期望 200 / 实际 403  (无权访问该店铺)
  [PASS] 演示模式：写方法缺头仍 400（空值守卫与身份无关）: 期望 400 / 实际 400
结果: 1/2 通过
```

**注意退出码**：脚本 `return 0 if passed == len(results) else 1` ⇒ 此处应为 **1**。
但**没有任何自动流程会看到这个 1**（见 §3.3）。

### 3.2 定性：**期望值过期（负资产），不是真回归**

**代码是对的**。铁证在 `backend/core/tenant/middleware.py:256-262`：

> `★★★ 第 177 轮：删掉「user is None ⇒ 直接放行」这一档。`
> `演示身份（无凭据 / demo-token）此前在这里整段跳过归属校验，于是「列表紧、单店松」`
> `—— 伪造 X-Shop-ID 即可读写任意店铺的业务数据。`
> `现在演示身份也走下面的 can_access_store：演示店铺（is_demo=True）⇒ 200；真实店铺 ⇒ 403。`

判定内核 `core/auth/accounts.py::_matches`（第 398-400 行）：

```python
if user is None:
    # 演示身份：只放行演示店铺。真实店铺一律不可见。
    return bool(is_demo)
```

而脚本造的是 `TenantB-Store`，`ensure_store()` **未设 `is_demo`** ⇒ 是**真实店铺** ⇒
**第 177 轮之后按设计就该 403**。

**实证（把「另一半」也验了，避免只验一半）**：探针 `r353/verify_demo_store_access.py`
造演示店 + 真实店，用无 token 请求逐条打：

```
判定内核 can_access_store(db, user=None, store)：
  [演示店 is_demo=True ] -> True  (期望 True)
  [真实店 is_demo=False] -> False  (期望 False)
端到端 get_current_shop_id（无 token = 演示身份）：
  [演示店] 放行(200) -> 'store_demo_4a0260'
  [真实店] 403 (无权访问该店铺)
结论：演示店 200 / 真实店 403 -> 期望过期（代码正确）
```

⇒ **演示能力完好**（老板演示不受影响）；403 是第 177 轮的**正确加固**。
出问题的是**门禁的期望值停在修复之前**（脚本 docstring 第 11 行同样过期：
「演示模式（AUTH_REQUIRED=false）→ **全部放行**（不破坏本地演示）」）。

### 3.3 根因（**比 3.2 更值得记**）：它不在任何自动入口

`backend/scripts/` 下 4 部脚本门禁的**真实**自动入口（AST 判据：只认
`subprocess` / `runpy` 一类**执行调用**的实参，含 `Path` 拼出的**变量**）：

| 脚本门禁 | 自动入口 |
|---|---|
| `check_alert_rules.py` | ✔ `tests/test_alert_rules_gate.py` |
| `check_compose_secrets.py` | ✔ `tests/test_compose_secrets_gate.py` |
| `check_multi_turn_memory.py` | ✔ `tests/test_agent_session_memory.py` |
| **`check_tenant_isolation.py`** | **★★ 无任何自动入口** |

- **没有 pytest 包装**：`tests/` 里对它的 3 处提及**全是注释 / docstring / assert 的字符串样例**
  （`tests/test_import_boundaries.py:24,166,228` —— 它被当作「跨包 import 私有符号」的**反面教材路径**引用），
  **没有任何一处执行它**。
- **CI 也不跑它**：`.github/workflows/ci.yml` 里 backend job 走 pytest；
  直接跑脚本的只有 `frontend` glob 与 `python scripts/check-cd-assets.py`（assets job）。

⇒ 这是本仓原则二的**教科书级反面样本**：
**一条判据「写了」「红了」，但价值为 0** —— 因为没有某次改动能让任何人看见它红。

★ **附带更正**：r350 报告 §5 记「后端 4 部脚本**由 pytest 包着跑**」，
本轮实测为 **3 部有包装 + 1 部裸奔**（当时把 `test_import_boundaries.py` 误点为它的包装）。

### 3.4 建议修法（两件事，都不大）

1. **修期望值**（改脚本的「演示模式」分支，约 10 行）：把
   「无 token 也放行（真实店）⇒ 200」改为**贴合第 177 轮口径**的两条：
   `演示身份 + 演示店 ⇒ 200` / `演示身份 + 真实店 ⇒ 403`。
   ★ 修完必须**反向注入**（把 `_matches` 的 `return bool(is_demo)` 改成 `return True`

### 3.5 它同时印证了什么

**★ 探针自纠留痕（本轮共 3 处，如实记录，防后人重蹈）**：

1. `name in tests_src`（字面量包含）⇒ 把「被 docstring 提到」判成「有人跑」→ **假阳性**；

## 9. 给下一次复审的三条（防再犯）

1. **「有没有接上」必须用 AST 问「是否被**执行**」，禁用字面量包含**
   —— 本轮同一个坑踩了两次：`name in tests_src` 把 docstring 提及判成「有人跑」（假阳性）；
   `strs[-1]` 因 `ast.walk` 是 **BFS 非源码序**取错段（假红）。
   ★ 判据写完先自问一句：**「哪一处改动能把它打红」**。
2. **注入探针的「钩子识别口径」必须跟着门禁写法演进**
   —— r351 把开口从 `process.env.LITERAL` 改成 `pick('NAME')`（动态键），
   r350 的探针认不出 ⇒ 8 道**已有开口**被判 NO-HOOK，会得出「r351 没落地」的**反向结论**。
   ⇒ 换写法时**同步改探针**；探针报 NO-HOOK 增多时**先怀疑探针**。
3. **「红着没人知道」比「红」更值得报**
   —— 本轮 `check_tenant_isolation.py` 1/2 通过，如果只按「一条红」记就漏掉了真正的病：
   它**不在 pytest、也不在 CI**。盘门禁时除了数「有几条」「红不红」，
   还要**逐条问：它红了谁会知道？**
