## 1. L3-11 —— 门禁「读集注入开口」补全

### 1.1 口径修正：r350 归档的「12 道 NO-HOOK」是**误判**，真实是 **9 道**

r350 的扫描器只匹配 `process.env.NAME` 的**点号形式**。而本仓既有范式是

```js
const pick = (env, fallback) => process.env[env] ? path.resolve(process.env[env]) : fallback
```

的**动态下标** `process.env[env]`。补充 `process\.env\s*\[` 这条形态后，实测
**HOOK-OK 29 / HOOK-OTHER 0 / NO-HOOK 9**：8 道真缺口 + 1 道配置面例外
（`check-eslint-ratchet.cjs`，其「读集」是 ESLint 配置而非源码，走 r349 的配置注入）。

> ★ 这是一条可复用的教训：**判「有没有开口」不能只认一种写法**；

### 2.2 ★ 一个必须先实测的设计前提：ContextVar **不能**跨任务边界回传

原打算「用 ContextVar 直接 `set(get()+ms)` 累加」。实测**证伪**：

```
$ python .workbuddy/probes/r351/l3_3_task_boundary.py
A_VALUE_IN_MW=0      (子任务 set 999 ⇒ 中间件读回 0)
B_BOX_IN_MW=777      (子任务改对象字段 ⇒ 中间件读回 777)
结论：只有【方案 B 可变容器】能跨任务边界回传 ⇒ 分段计时必须用可变容器
```

根因：中间件的 `call_next` 会**另起一个 asyncio task**（starlette `BaseHTTPMiddleware`
的 anyio task group），而 Task 创建时 `copy_context()` ⇒ 子任务的 `set()` 只改自己那份**拷贝**；
但 context 拷贝**共享同一对象引用** ⇒ 改可变对象的字段能回传。

⇒ 实现定为「**一个 ContextVar 承载一个 `RequestTiming` 可变对象**，下游只改字段」。
**反向注入自证**（`revinject_timing_snapshot.py`）：把它换成「快照式读 ContextVar」，
`tests/test_request_timing.py` 红 **5** 条（含关键的跨任务边界用例），还原后全绿。

## 3. L3-4 —— prompt 指纹（渲染留痕 + 返回注解去擦除）

### 3.1 原来到底缺什么（两个**互相独立**的缺口）

| # | 缺口 | 实测形态 |
|---|---|---|
| ① | **注解擦除** | `ai_infra/base_agent.py:824` 写 `-> str`，而运行期返回的是 `RenderedPrompt`（携带 `version` / `fingerprint`）。`RenderedPrompt` **是** `str` 的子类 ⇒「返回值的运行期类型」这件事**永远判不出来**，只能从注解上看 —— 而注解恰好把它说成了 `str`。 |
| ② | **元数据没人打出来** | 全仓 `version` / `fingerprint` 只有**注册期**一行 `logger.debug`（`dashscope_client.py::register_prompt_template`）。生产默认 `log_level=INFO` ⇒ **那行永远不打印**。于是「回答质量突变时是哪一版提示词」仍然只能翻 git log 猜。 |

> ★ ② 与本仓 L3-1 / L3-2 同族：**配置 / 元数据写了，却从未真正生效**。

### 3.2 落点选择（为什么留痕不住在 `get_prompt_template`）

留痕写在 `ai_infra/llm/prompt_spec.py::render_prompt()` —— **全仓唯一的渲染实现**
（`PromptSpec.render()` 与模块级 `get_prompt_template()` 都汇到它）。

实测反例证明「在消费方那层留痕会漏」：店秘书把返回值再加工成普通 `str` ——

    ⑥ 再加工后还是 str          : True | 还带 fingerprint 吗 : False
    （`modules/secretary/agent.py::_with_shop_fact()` = f"{base_prompt}\n\n{text}"）

即：**在消费方留痕，凡是「拼过之后再发」的路径都会变成没有痕**。

另外两条刻意选择：

- **级别 INFO**（不是 DEBUG）：生产默认 `log_level=INFO`（`core/logger.py::_add_sinks`），
  写 DEBUG 就是把缺口 ② 换个地方再犯一次。
- **只记变量名、不记变量值**：值是业务数据（店铺事实等），日志不该承载它。

### 5.3 本轮修掉的一个**真缺陷**：失败分支的审计留痕被静默回滚

⇒ 修法：失败分支在 `raise` 前**先 `await db.commit()`**（两处）。

## 6. P0-7 B 档 —— 提示词版本的 DB 覆写层

### 6.1 原来缺什么

A 档齐备（`PromptSpec` 带 `version`/`fingerprint`/`required_vars`），
但 **B 档 DB 覆写层完全没有**：`prompt_versions` / `PromptVersion` 只活在文档里，
**无表、无迁移、无服务、无端点**。⇒ 改一句提示词要改代码 + 重新发版；
而 `version` 是**人手写**的，没有"语义升级必须递增"的手段。

### 6.2 分层：`ai_infra` 硬红线决定了拆成两半

本仓有硬红线：**`ai_infra` 不得 import `modules.*`**（`tests/test_infra_layering.py`
拦过历史上 4 处真实泄漏）。所以覆写层**拆两半**：

| 半 | 住哪 | 职责 |
|---|---|---|
| 应用侧 | `ai_infra/llm/prompt_overrides.py` | 管**内存注册表**（渲染路径打的表）：`_prepare()` 两道闸门 + `apply_override` / `reset_override` / `validate_override` / `describe_override` / `preview_override` / `applied_overrides` |
| 表侧 | `modules/prompt_versions/`（`db_model` / `schemas` / `service` / `router` / `__init__`） | 管 **DB**：CRUD + 状态五态 + 表↔内存同步；**唯一同步点**在 `service.py` |

### 6.3 本轮修掉的**真缺陷**：写口「先落库、后应用」造成虚假陈述

一条**变量集与基线不符**的正文，会被写进库；而 `_status_of()` 只看
「enabled 且基线指纹对得上」⇒ 判 `active` ⇒ **界面显示「覆写生效中」，
线上却跑源码版**（`apply_all_overrides()` 应用时被 `vars-mismatch` 拒掉）。

⇒ 修法三件：
1. **两道闸门收成唯一实现** `_prepare(name, *, content, version, base_fingerprint)`
   （依次判 `unknown-name` / `stale` / `invalid` / `vars-mismatch`，**不做任何 mutation**），
   原有两个入口都变成它的薄壳 ⇒ 本仓铁律「同一判定两份实现 ⇒ 至少一份永远测不到」；
2. 新增出口 `validate_override(...)`（**只校验不应用**）；
3. **写口在落库之前**调它 ⇒ 不符即 `InvalidOverride` → **400（detail 带 reason）**，
   且失败也写审计。

另修：`_to_item()` 把 **`applied`（运行态）与 `status`（配置态）分开报** ——
「库里启用了」与「内存里真的生效了」是两件事，合并报就是虚假陈述。

## 7. P0-2 PITR —— WAL 归档 + 物理基线 + 恢复演练

### 7.1 原来缺什么（r350 实测口径）

    ✘ `wal_level` / `archive_mode` / `pg_basebackup` 在**生产代码**中 0 命中

`backup_db.py` 做的是**逻辑备份**（`pg_dump`）：恢复粒度 = **一次 dump 的瞬间**。
它答不了这一类问题：

> 「今天 14:03 那条 UPDATE 把 380 条订单状态刷错了 —— 恢复到 14:02 的样子，
>   但 14:00 之后新签的那两单**要保留**。」

`pg_dump` 只有"整库回退到昨天 23:00"这一个答案，代价是丢掉从那以后的一切。
**PITR** 才是那个答案：`物理基线 + 之后每个 WAL 段` ⇒ 可恢复到**任意一个
LSN / 时间点 / 具名还原点**。

### 7.2 落地

| 文件 | 内容 |
|---|---|
| `scripts/pg_pitr.py`（新） | 五个子命令：`status` / `enable` / `archive-fetch` / `basebackup` / `drill` |
| `core/observability/metrics.py` | 新增 `pitr_runs_total{kind,status}` + `pitr_wal_archive_bytes`（注册进 `_REGISTRY`） |
| `core/backup/tasks.py` | 新增 `TASK_WAL_FETCH` / `TASK_PG_BASEBACKUP` + 两个 Celery 任务（退出码翻译成异常、异常不吞、各自记指标） |
| `core/redis.py` | beat 两条：`wal-archive-fetch`（**每 15 分钟**，分钟偏移 7 避开 `*/5` 家族）、`pg-basebackup-weekly`（**周一 2:11**，排在每日 dump 2:41 之前） |
| `observability/alert_rules.yml` | 新 `storekeeper-pitr` 节三条：`WalFetchFailing` / `PitrBasebackupFailing` / `PitrBasebackupStalled` |

★ 演练的**判据设计**是重点：**既**断言还原点之前的 A **在**、**又**断言之后的 B **不在**。
只有一边成立都可能恒真（比如恢复根本没跑、库是空的）——
两条一起才证明"恢复确实**停在了那个点**上"。

后者依赖时钟粒度与事务提交时间对齐，前者是 WAL 里一条明确定位的记录。

### 7.5 未验证项（诚实标注，附一条设计取舍）

1. **归档目录落在容器的可写层**（`/var/lib/postgresql/wal-archive`），不在卷里 ——
   因为 `my-postgres` 是 `docker run` **手工创建**的，没有第二个挂载点，
   而给已有容器加挂载**只能重建容器**。后果：
   `docker stop/start` 归档段**还在**；**`docker rm` 未外送的段全丢**。
   ⇒ `archive-fetch` 是**必需步骤**而非可选优化（故它有自己的 beat 条目与告警）。
   生产部署走 `docker-compose.yml` 的 `walarchive` 卷（本轮已加，路径与
   `ARCHIVE_IN_CONTAINER` 一致 ⇒ 将来按 compose 起库即天然分卷）。
2. **`pg_basebackup` 未做过"基线本身损坏"的演练**：本轮证的是"基线 + 归档能恢复到指定点"，
   没有注入"基线 tar 被人截断"再看恢复是否**合理失败**。
3. **归档段与基线的异地副本未做**：全部落在本机 `backups/`（磁盘故障即同时丢）。
   本仓 r350 把"异地"列为 P0-2 的剩余项，本轮**未动**。
4. **`archive_command` 用 `cp` 到本地目录**（不是流式外送）：段积压时会占容器磁盘。
   本轮没有为它设容量告警。
