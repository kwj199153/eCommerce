### 判据 1 为什么是"等价实验"

口令不在我手上（`/root/.demo_pw`，600，也不该进仓）。我没有伪造 200，而是用
**同一个代码路径**造了一个可控前提：

- `tests/test_demo_login_alias.py` 里把 `config.demo_account_email` **临时**指向一个
  `make_user` 造的临时用户（口令由测试自己设定），打开别名 ⇒
  用 `admin` + 那个口令登录 → **HTTP 200 + `access_token`**，且 `/auth/me`
  返回的是那位用户而不是字符串 `admin`。
- 该临时用户与其数据在用例结束时被 `make_user` 回收。

⇒ 「别名 → 查到用户 → 口令正确 → 发 token」这段在我们这边**已经被自动化跑通**。
真演示号的那一跑，请你按工单第五节复跑 —— 差别只在"口令是哪一串"，不在代码。

### 判据 5 是这次的重点，讲清为什么没被绕开

别名只影响"这次输的字符串去查谁"，签出来的 token 里仍是那个用户真实的
id / email ⇒ `is_demo_account()`（`core/auth/demo_identity.py:205`，按 email 比对
`config.demo_account_email`）判定完全不变，三条 403 一条不少，且实测就是 403。

## 四、判据的反向注入（证明不是恒绿）

把别名分支整个去掉（退回"前端不拦、后端不认"），重跑 6 条测试：

| 用例 | 注入前 | 注入后 |
|---|---|---|
| 别名 + 正确口令 → 200 + token | PASS | **FAIL** |
| 审计记真 email | PASS | **FAIL** |
| 大小写 / 空白不敏感 | PASS | **FAIL** |
| 原 email 仍是有效登录名 | PASS | PASS（不受别名影响，符合预期） |

**红的正好是"admin 能登进去"那三条，对照组全绿** ⇒ 红的是别名，不是整条登录链路。
还原后 `router.py` 的 sha256 逐字一致（`a88c3223…2946`），6 条复跑全绿。

端到端探针也做了同一个注入（`DEMO_LOGIN_ALIAS=` 空跑的第二个实例）：
`admin` 变成 `reason=unknown_email`、审计记成 `admin` ⇒ 判据 FAIL。

## 五、★ 一个必须交代的坑：我第一版判据是假绿的

端到端探针第一版按 `email = demo_account_email ORDER BY created_at DESC LIMIT 1`
取审计行。于是**上一次探针自己留下的 `bad_password` 行**会被当成本次结果 ——
把 `DEMO_LOGIN_ALIAS` 置空做反向注入时，判据**照样全绿**。

改成：每次跑生成唯一 `User-Agent` 标记，只查"本次探针造出来的行"，并断言
条数为 1。同样的纪律在恒等式判据里已经踩过：**判据必须取自"只有改动成功才
可能出现"的集合**，否则它测的是上一轮的残留。

写在这里是因为：如果你按这个思路自建检查，很容易复制同一个错误。
