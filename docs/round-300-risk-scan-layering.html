风险识别耗时 —— 分层方案

第 300 轮 · 回应「仅 20 条评论就要风险识别非常久，不符合实际」 · 状态：A + C + D 已落地并实测（B 后台异步本轮不做）

一句话结论

慢的不是「条数」，是 逐条串行调用模型、且每次都让模型把理由写出来。 落地三件事之后：默认浅层（2.9 ms），按需深扫 19 条 1.18 s（对照真机 43.4 s ⇒ 36.7×）， 判定质量 P/R/F1 = 1.00。

一、老板那一问的判决：选 D 会重犯旧错吗？

问：「选 D 的话会犯你之前说的以前犯过的错吗？」
答：宽泛版会，收紧版不会。 判决探针 decide_d_safety.py（7 样本 × 4 种 LLM 出口 = 28 格）： 

D-宽泛（rule.categories 非空即跳过）  改变 decision：3 格
  T_EMOTION llm=unknown    unknown -> clean
  T_EMOTION llm=hit_r3     risk    -> clean   ← 漏报
  T_EMOTION llm=hit_r3r4   risk    -> clean   ← 漏报
D-收紧（rule.risk_categories 非空才跳过）  改变 decision：0 格

机制级理由：fuse() 在命中四类时提前 return、压根不读 LLM 的 decision ⇒ 四类命中时「不送语义」是无操作；而只命中 r5（高情绪）时规则判 CLEAN、fuse() 要读 LLM 的结论 ⇒ 把它也短路掉就是 让下游通道零参与，与第 246 轮「关键词短路抢在技能注入之前 return」同构。

⇒ 硬约束：短路条件必须是 rule.risk_categories，不许写成 rule.categories。已用 AST 门禁 + 反向注入双重钉死。

二、分层三步（service.scan_reviews_risk 的 deep 分支）

① 规则通道 全量先跑（0.15 ms/条）→ 它同时决定「谁不用送语义」
② rule.risk_categories 非空 ⇒ 不再送语义（D）
③ 其余条目 打包成一次批量语义调用（C），按序号回填

批量协议（压缩输出的三态必须齐）： 

输入： [{"n": 1, "text": "..."}]            ← 用序号不用 review id（模型复述长 id 会错）
输出： {"1": "", "2": "?", "3": "r2:high|原文逐字片段"}

  ""  ⇒ clean     （模型明确判无风险）
  "?" ⇒ unknown   （模型拿不准 —— 与 clean 方向相反，不可合并）
  "cat:level|证据" ⇒ 命中；证据必须能回到原文
  • 缺项 / 解析失败 / 调用异常 ⇒ 一律 unknown（fail-closed），绝不猜 clean。
  • max_tokens 逐次随条数放大 —— get_llm() 按模型名缓存单例，建实例后再传参数无效（会静默截断）。
  • 拆包上限 10（换失败半径，不为省钱），多包并发发。
  • 兼容模型常见的 4 种返回形态 —— 只认一种会把「格式不合我意」记成「模型判不出来」。

四、已知口径差异（如实记在案）

4.1 批量版用 clean 的地方，逐条版常给 unknown

51 条送语义的样本里 14 条 decision 不一致，全是 逐条=unknown → 批量=clean，没有一条是「批量漏掉 risk」；两轮稳定复现。 例（gold 全为 none，批量判 clean 是正确方向）： Colour is darker than the photos ... Not a deal breaker、 Seal gave up after a month ... everything else still works。

⇒ 影响：界面上的「未定论 N」会变小。这是提示词形态效应（逐条版更容易说 「拿不准」），不是判定能力变化。好处是人工复核队列变短；代价是 「未定论」这个数字不能跨版本比较。已写进 scan_llm_batch 的 docstring —— 它依赖模型行为，离线门禁钉不住，只能靠读数留痕。

4.2 复测中发现的两条误报 → 两条提示词同补陷阱规则

五、为什么不选 B（后台异步）

B 不降总耗时、只改观感，但需要任务态存储 + 轮询。分层之后总耗时已降到约 1.2 s —— 等 1 秒不值得引入一套任务状态机。保留为「条数上调到几百条时」的候选。
