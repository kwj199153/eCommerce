# `knowledge_docs` 0 行 —— 处置方案（第 287 轮，待老板拍板）

> 本文只给方案，不实现。背景：第 285 轮「客服域能不能拿出真数据」审查把
> 「缺数据」分成三类（A 接错源 / B 真缺数据 / C 没接），`knowledge_docs`
> 当时归到 **B 类**。本轮做第 2 项（`review_dispositions` 出口）时顺手做了
> 更细的取证，结论比「B 类」更具体 —— 见下。

---

## 一、现状取证（都是实测，不是推断）

| 项 | 实测结果 |
|---|---|
| `knowledge_docs` 行数 | **0**（全库，4 个店铺都 0） |
| 对照：`knowledge_faqs` | 72 行（每店 18） |
| 对照：`knowledge_bases` | 4 行（每店 1 个默认库） |
| 后端端点 | **齐全**：`POST /knowledge-base/docs`、`GET /{doc_id}`、`DELETE /{doc_id}` |
| 前端写入入口 | **有**：`FaqKnowledgeBase.vue:414` 的 `store.uploadDoc(file)` |
| 前端读取/展示 | **有**：`stores/knowledge.ts` 的 `docs` state + 列表渲染 |
| **检索消费方** | **零** —— 全仓 grep `KnowledgeDocRecord` / `knowledge_docs`，除 `knowledge_base` 模块自身的 CRUD 与建表登记外，无任何消费点 |
| `ai_infra/rag/hybrid_engine.py` | 只吃 `add_faq_knowledge_base(faq_items)`，即**只检索 FAQ**，没有文档那一路 |
| db_model 的 docstring | 写着「智能客服 **RAG 切片检索**的输入源」 |

### 这条 docstring 是假承诺

`KnowledgeDocRecord`（`modules/knowledge_base/db_model.py:143`）的注释声称文档
是客服 RAG 的输入源，但**没有任何代码读它**。按本仓既有判据，这属于
「声明承诺型假门禁」——注释说有、消费点为零。

### 所以它不是单纯的「B 类缺数据」

准确的分型是：

- **写入路径存在且可用**（前端上传 → content 一并提交 → 落库），0 行的直接原因是
  **没有人上传过** —— 这部分确实是 B 类（真缺数据）。
- **但就算上传了也没有出口**：文档进去只能被列出来看一眼，不参与任何检索。
  这部分是 **C 类（没接）**。

⇒ 只灌数据（让它不为 0）能解决「页面空」，**不能解决「文档没用」**。

## 二、四个方案

### 方案 A · 只灌演示文档（最小）

- 做什么：新增 seed，灌 3~5 篇带正文的电商客服素材（退货政策 / 物流时效 /
  质保条款 / 尺码指南 / 支付与发票）进 `knowledge_docs`。
- 解决：页面不为 0；「AI 拆分」类功能有输入。
- **不解决**：文档仍然没有检索出口。
- 工作量：小（1 个 seed 脚本 + 5 篇素材文本）。
- 风险：把「0 行」变成「5 行但依然没人读」，是**用数据掩盖缺口**。

### 方案 B · 文档拆成话术，出口接 `knowledge_faqs`（**推荐**）

- 做什么：新建 `modules/knowledge_base/ai_split_faq.py`，照
  `modules/platform_rules/ai_split.py`（`split_rules_from_doc`）的既有范式：
  **整篇读正文 → LLM 提取结构化问答条目 → 落 `knowledge_faqs` → 三层去重**
  （预查重 + 人工复核 + 持久化防重）。配套加一个端点 + 前端按钮。
- 为什么出口选 `knowledge_faqs`：第 286 轮刚把客服话术的真源从内存 mock
  切到 `knowledge_faqs` 表 —— 拆出来的条目**立刻被客服检索消费**，
  文档这才真正进入业务链路，闭环成立。
- 顺带修掉上面那条假 docstring。
- 工作量：中（1 个拆分模块 + 1 个端点 + 前端按钮 + 门禁 + 测试）。
- 依赖：**文档必须有正文**（`content` 非空）。现状 0 行 ⇒ 需要先做 A，
  或让用户上传带正文的文档。空正文时对拆分**明确报错**，不编造。
- 收益可验证：上传一篇退货政策 → 拆出 N 条 → 客服问「怎么退货」能命中
  **来自这篇文档**的条目（可钉成门禁）。

### 方案 C · 切片 + 向量检索（最重）

- 做什么：建切片表、灌向量库，客服检索融合两路召回（FAQ + 文档片段）。
- 收益：长文档问答能给出原文出处（「质保多久」→ 引政策 PDF 第几段）。
- 代价：与第 286 轮刚收口的「FAQ 真源」叠加复杂度；排序融合、引用呈现
  都要新做；切片粒度调不好会明显掉质量。
- 工作量：大。

### 方案 D · 只改口径（零成本，可与任一方案叠加）

- 把 db_model 的 docstring 改成如实描述（当前是「登记素材 + AI 拆分的输入源」，
  不是「RAG 切片检索的输入源」）；
- 前端文档区明示「文档素材暂不参与客服检索」。
- **如果三个方案都不做，这一条至少要做** —— 假注释会误导下一个接手的人
  （本轮我就是被它指引着去找「RAG 那一路」的，结果那一路根本不存在）。

## 三、对比

| 方案 | 解决「0 行」 | 解决「没出口」 | 修假承诺 | 工作量 | 可验证的终态 |
|---|---|---|---|---|---|
| A 灌演示文档 | ✅ | ❌ | ❌ | 小 | 页面有 5 篇，仍然没人读 |
| **B 拆成话术** | ✅（需先有文档） | ✅ | ✅ | 中 | 上传文档 → 拆成条目 → 客服检索命中该条目 |
| C 切片向量检索 | ✅（需先有文档） | ✅ | ✅ | 大 | 长文档问答带原文出处 |
| D 只改口径 | ❌ | ❌ | ✅ | 极小 | 注释与 UI 不再撒谎 |

### 我的建议：**先 B，配套的 A（3~5 篇素材）与 D（改注释）一起做**

理由：

1. B 的出口正好是上一轮刚接通的 `knowledge_faqs`，**同一条链上一头一尾**
   —— 上游（文档）接进来，下游（客服检索）立刻吃得到，闭环最短。
2. 仓内已有同构实现（`platform_rules/ai_split.py`）可对账，不是从零设计；
   它的「空正文明确报错、绝不编造」口径与本仓 fail-closed 惯例一致。
3. C 的增量收益（原文出处）在「话术」这个场景里价值有限 —— 拆成结构化条目后
   本来就是一句一答，比引一段原文更好用。
4. 只做 A 会得到一个「看着有数据、其实没用」的表，正是这几轮一直在清的债。

如果老板更看重「能引用原文出处」，或预期会上传很长的政策/手册类文档，
再考虑 C（可视为 B 之后的第二阶段：先有条目级出口，再补片段级召回）。
