## 二、P3 回答：**阿里（DashScope）现在能不能接真思考链？**

### 结论：能用，但有两个前提；而**本仓现在一个都还没满足**

#### 前提 ① 模型 ID 必须显式换成「混合思考模型」——`qwen-max` 这个别名不行

实测（`238q` / `238r` 探针，流式，`enable_thinking=true` 平铺传入）：

| 模型 | 思考字数 | reasoning_tokens | 首思考 | 首正文 | 总时长 |
|---|---|---|---|---|---|
| **`qwen-max`** | **0** | None | — | 0.43s | 1.20s |
| `qwen-plus` | 1595 | 863 | 0.36s | **11.18s** | 11.85s |
| `qwen-flash` | 1358 | 798 | 0.33s | 5.21s | 5.50s |
| `qwen-turbo` | 312 | 178 | 0.38s | 1.60s | 1.87s |
| `qwen3-max` | **2903** | — | 1.2s | **44.04s** | 45.54s |

★ `qwen-max` 传 `enable_thinking=true` 返回 **HTTP 200 但一个字都不回**，且 `completion_tokens` 与不开思考**完全相同（26）**
⇒ 参数被**静默忽略**。旁证：同题同参换 `qwen3-max` 回 2903 字。
**⇒ `qwen-max` 这个别名不指向混合思考模型。**

#### 前提 ② 本仓的取数层会**把思考链整个丢掉**

`langchain-openai 1.2.2` 的 `_convert_delta_to_message_chunk`（`chat_models/base.py:428-468`）
**只取 `content` / `function_call` / `tool_calls`**；文件头第 8 行与第 587 行注释自认 `reasoning_content`
"**not extracted**"。

⇒ **只开 `enable_thinking` 而继续走 `ChatOpenAI` = 最坏组合**：
思考 token **照付钱**、首 token **更晚**、而思考链**一个字都拿不到**。

### 好消息：取数不难，工程量集中在「通道 + 渲染」

- `openai 2.40.0` 能读到：实测 `ChatCompletionChunk.model_validate(...)` → `delta.reasoning_content == '先想一下'`（落在 `model_extra`）。
- 栈 B 的 `DashScopeLLM` 本就是 **httpx 直连**，天然可取。
- ⇒ P3 的工作量在「新增 `reasoning` 事件通道 + 前端渲染面板」，**不是**「攻克对端」。

### 成本提醒：思考链是**净成本**，不是白送的体验改善

`qwen-plus` 开思考 ⇒ 首正文 **11.18s**（比不开思考慢约 20 倍）。想清楚要付这个代价再上。

## 六、补充实测：那 2.5s「固定开销」到底是什么（修正第三节的归因）

第三节写的是「与模型无关，得从会话解析 / checkpoint / prompt 组装下手」。**更精确的答案在后半句**——
它主要是**我们自己发出去的 prompt 太大**，不是"服务端代码慢"。

### 证据 1：TTFT 与输入长度近似线性（探针 `238s`）

同一个模型、同一个问题，只改输入长度：

| 输入字符 | `prompt_tokens` | TTFT |
|---|---|---|
| 0 | 19 | **0.43s** |
| 800 | 502 | 0.53s |
| 3 000 | 1 829 | 0.88s |
| 12 000 | 7 261 | **2.41s** |

⇒ 最长/最短输入 TTFT 增幅 **462%**，约 **+0.28s / 1000 输入 token**。

### 证据 2：把**真实的自研 prompt** 发出去量一次（探针 `238t`）

| 用例 | `prompt_tokens` | TTFT 中位 |
|---|---|---|
| A 裸问（无 system / 无 tools） | 13 | 0.47s |
| B + 真实 system prompt（2 524 字符） | 1 469 | 0.48s |
| C + 真实 tools（18 个，schema 11 492 字符） | **4 835** | **1.64s** |
| **D 真实完整组合** | **6 286** | **2.25s** |

### 结论（这条比"换模型"值钱得多）

- 秘书一轮的输入是 **6 286 token**，其中 **工具 schema 占 4 822（77%）**；
  而 system prompt 只占 1 469（23%）——**工具定义才是最大的那块**。
- 那 2.5s 里，**模型 prefill 就吃掉 ≈2.25s**（其余是会话解析 / checkpoint / 段落注入）。
- ⇒ **第一杠杆是砍工具 schema**，不是换模型（P2 换模型对 TTFT 的贡献 ≈ 0.05s，见第五节）。
  18 个工具若能为「第一轮」收敛到 6~8 个，输入约降到 2 000 token，
  按 0.28s/1000 token 估算 **首字可再提前 ≈1.2s**，并同时降低**每一轮**的输入计费。
- ⚠️ 但这是**行为变更**（工具少了，模型能直接调的能力就少了）⇒ 需要老板先定「哪些工具第一轮不该出现」，
  不是可以默默做的优化。

**探针清单**：`238q`（思考链可用性 / 各模型 TTFT）、`238r`（P2 候选模型关思考对照）、
`238s`（TTFT×输入长度）、`238t`（真实 prompt 的 prefill 代价）、`238k`（真 uvicorn 端到端）。

## 七、模型选型：要不要把所有 Agent 都改掉？（实测回答）

### 现状（实测）

- 全仓 **8 个 Agent**（`secretary` / `ad_analysis` / `aigc_media` / `competitor_intel` /
  `customer_service` / `listing_generator` / `product_research` / `review_analyst`）
  **全部共用同一个** `config.llm_default_model = qwen-max`；
  全仓仅 `core/config.py:484` 一处定义，**没有任何按 Agent 的模型覆盖**
  （`FAST_FIRST_ROUND` 是唯一的按 Agent 开关，且只对 secretary 打开）。
- 两条 LLM 栈：栈 A（图内核 `_llm_with_tools`）只有 `secretary` / `review_analyst`；
  其余 6 家走栈 B（`llm_stream` 业务原语，天然有打字机）。

### 先纠正一个措辞

「`qwen-max` 不是思考模型」的准确含义是 **`qwen-max` 这个别名不指向混合思考模型** ——
传 `enable_thinking=true` 返回 HTTP 200 但回 **0 个思考字**，且 `completion_tokens`
与不开思考**完全相同（26）**；同题同参换 `qwen3-max` 回 **2903 字**。
**不是模型坏了，是别名指向的不是那一档。** 所以「改」的正确说法是
「给需要思考的场景显式点名 `qwen3-*`」，而不是「`qwen-max` 不能用」。

### 结论：**不建议全改**，三条理由都有实测支撑

1. **思考是净成本**：`qwen-plus` 开思考首正文 **11.18s**、`qwen3-max` **44.04s**，
   比不开思考慢 20~100 倍。
2. **换模型对首字几乎无用**：TTFT 中位 `qwen-flash` 0.34s / `qwen-turbo` 0.42s /
   `qwen-max` 0.46s / `qwen-plus` 0.50s ⇒ **全区间只差 0.16s**。
3. **`qwen-max` 在「工具路由」这类任务上不是瓶颈**：`238x` 用 14 条真实 query × 6 次，
   绝大多数是 6/6 稳定。

### 如果要改，按用途分档（而不是全改）

| Agent | 交互性 | 建议 | 依据 |
|---|---|---|---|
| `secretary` | 强交互（老板等首字） | **保持 `qwen-max`**（第一轮已由 P2 走快模型） | 首字敏感，开思考是负收益 |
| `customer_service` | 强交互 | 保持 | 同上 |
| `competitor_intel` / `product_research` / `review_analyst` | 后台长任务 | **可试点 `qwen3-max` + 开思考** | 用户不在等字；但**必须先做质量对照**再定 |
| `ad_analysis` / `aigc_media` / `listing_generator` | 半交互 | 暂保持，等明确质量诉求 | 无实测证据表明换模型更好 |

★ **前提工程**：现在**没有「按 Agent 配模型」的能力**（只有全局 `llm_default_model`）。
要分档得先补这个能力 —— 这是 P2 留下的口子。

★ **更值钱的结论（已被第十节修正）**：延迟的杠杆**不在模型，而在输入规模与缓存计费**（第九节的「−1.2s」经复查不成立，见第十节）。

## 九、缓存击穿（⚠️ **本节结论已被第十节实测推翻，勿单独引用**）

### `238y`：隐式缓存本来就在工作

阿里百炼有**隐式上下文缓存**（命中后输入按 **20% 单价**计费）。实测：

- 干净 prompt（system 固定 + 18 工具）连发 4 次：
  `cached_tokens = 4096 / 6287 = 65%`，**第 1 次就命中**，首帧 843~921ms
- 在 system **末尾**追加一个**每轮变化**的字符串：
  `cached_tokens` 掉到 **0~1024**，首帧 **2080~2576ms**

### `238z`：四组对照（同组连发 3 次，取末次 = 缓存最成熟）

| 装配方式 | 首帧中位 | cached_tokens |
|---|---|---|
| A `system` 固定 | 955ms | 4096 |
| B `system + sections`（**现状**） | **2362ms** | **0** |
| C `system + plan_block`（**现状**） | **2103ms** | 1024 |
| D `system` 固定 + sections 移到 user 侧 | **830ms** | **4096** |

### 根因

`ai_infra/base_agent.py::_system_prompt_with_plan`（1110-1141 行）每轮现算并拼接：

```
parts = [self.system_prompt] + sections + PLANNING_GUIDE + plan_block
```

其中 `sections`（记忆 / 上下文注入）与 `plan_block`（当前计划）**每轮都变**
⇒ **击穿 system 之后（含 tools）的整段前缀缓存**。

**代价**：多轮会话 / 有记忆注入时，每轮白付 **≈1.2 秒首帧**，且输入按**全额**计费
（而不是 20%）。

### 修法方向（不是直接改，要先验证）

- `PLANNING_GUIDE` 是**常量**，留在 system 无害 ⇒ **只需处理 `sections` 与 `plan_block`**
- 把这两段从 system 挪到**消息侧**（`238z` 的 D 组证明挪走后缓存恢复 4096）
- ⚠️ **不能简单塞进 `messages` 历史**：1129-1131 行的注释说明「拼进 system 就是为了
  躲 `trim_history()` 裁剪」。要挪到**当前轮、不被裁剪**的位置
- ⚠️ 挪动后需**语义保真验证**（system 里的内容 vs user 里的内容，模型权重不同）

### 与第八节的关系（顺序不能反）

缓存命中后，那 65% 的输入只按 20% 计费、prefill 也快 ⇒ **砍工具的收益会大幅缩水**
（被砍掉的部分本来就在缓存里）。
⇒ **先修缓存，再评估要不要砍工具。**

### 探针清单（本轮新增）

`238u`（工具集规模×首帧）、`238v`（schema 构成拆解 + 保真初测）、
`238w`（砍 `list_*` 的行为对比）、`238x`（三配置×6 次稳定性）、
`238y`（缓存命中实测）、`238z`（缓存装配四组对照）。

⚠️ **口径说明**：`238u` 与 `238z` 的**首帧绝对值不一致**（同为 18 工具：2440ms vs 955ms），
原因是两次的 tools 序列化方式不同（手写 vs LangChain 官方 `convert_to_openai_tool`）
导致命中不同的缓存块，**尚未查清**。
⇒ **首帧结论以 `238z` 为准**（同组连续、缓存状态可控）；`238u` 只采信 `prompt_tokens` 差异。

## 十、★ 对第九节的修正：实测**推翻**「每轮击穿 −1.2s」

> 触发：回答老板两个问题时回头复查第九节的**前提**（「`sections` / `plan_block` 每轮都变」），
> 发现那是 `238z` 用「第 i 轮」这个 **`i` 人为制造的变化**，不是真实行为。
> 本节用 `238aa` / `238ab` 重做，结论与第九节相反。

### 修正 1：真实 `sections` 在同一会话内**值不变**

触发注册后（`('long_term_memory','skills_catalog','skills_selected')`）连取两次：

- 第1次 = 第2次 = **1 段 / 181 字符，内容完全相同**
- 匿名对照 = 0 段 / 0 字符
- **库里 9 个用户，只有 1 个有记忆条目**（且 `probe_mem_*` 是测试残留）

⇒ 「每轮现算」≠「每轮都变」：provider 每轮被调用，但**同一会话读出来的是同一份内容**
⇒ **不击穿缓存**。

### 修正 2：`plan_block` 从「无」到「有」是**纯尾部追加**

真实完整 system（system_prompt 2524 + sections 181 + PLANNING_GUIDE 185）：

- 轮1（无计划）= 2894 字符 / 轮2（有计划）= 2940
- **最长公共前缀 = 2894 = 轮1 全长（100%）** ⇒ 轮1 是轮2 的**真前缀**

⇒ 追加式变化**缓存友好**，不是击穿。（238aa 首版也得到过同一数字，但那次是空 sections 的巧合。）

### 修正 3：位置规律成立 —— 但代价发生在「计划真的变动的那一轮」

修正版定序（变化**每次不同**；首帧抖动 ±300ms，故 **`cached_tokens` 才是稳定判据**）：

| 组 | 变化位置 | 首帧（两轮） | cached_tokens（两轮） |
|---|---|---|---|
| H1 / H5 | 全固定（基线） | 944 / 857ms | **4096 / 4096** |
| H2 | `tools` 变 | 2166 / 1841ms | 2048 / 1280 |
| H3 | system **尾部**变（= `plan_block` 位置） | 2260 / 1948ms | **1024 / 1024** |
| H4 | system **中部**变（= `sections` 位置） | 2746 / 1973ms | **0 / 0** |

⇒ **规律**：变化点越靠前，损失越大（**4096 → 1280 → 1024 → 0**）。
`sections` 恰好插在 system **中部**（实测突变点第 2712 字符）—— 位置最差；
`plan_block` 在**末尾** —— 位置次差。

⇒ 但两者**真实触发频率**都远低于「每轮」：
`sections` 稳定 ⇒ 几乎不触发；`plan_block` 只在 todo 状态更新时变 ⇒ **仅多轮任务进行中才逐轮触发**。

### 修正后的口径（替换第九节末段）

| 第九节原话 | 修正后 |
|---|---|
| 「多轮会话 / 有记忆注入时，每轮白付 ≈1.2 秒」 | **错**：sections 稳定 ⇒ 不触发；仅 todo 变动那一轮才有代价 |
| 「路线 3：零行为变更，实测 −1.2s」 | **收益被高估**：应表述为「计划变动那一轮省一次 messages 段重算（cached 1024→4096）」 |
| 「先修缓存，再评估要不要砍工具」 | 顺序仍对，但**理由变了**（见下） |

### 旁证：服务端缓存是**按段 + 按块（约 1024 token）**的

cached 梯度用「单一前缀块」解释不通，用「分段缓存」完全自洽：

- 只改 `tools` ⇒ **messages 段仍整体命中**（≈1560 token）⇒ 报 1280~2048
- 只改 system **中部** ⇒ messages 段几乎全废 ⇒ 报 **0**
- 只改 system **尾** ⇒ 命中 messages 段前部 ⇒ 报 **1024**

⇒ **`tools` 段是独立缓存的**：sections / plan_block 怎么变，都**不动 tools 段那 4800 token**。
（这也顺带解释第九节末尾「`238u` vs `238z` 首帧不一致」：两次 tools 的**序列化字节不同** ⇒ 落在不同缓存段。）

### 这对「要不要砍工具」意味着什么

- 砍工具**不省 prefill**（tools 段本来就在缓存里），省的是**计费**（命中按 20% 单价）
- 238t 的「工具 schema 占输入 77%」仍成立，但那是**首轮无缓存时**的代价
- ⇒ 砍工具的收益应表述为「**每轮固定省一份输入计费**」，**不是**「省 1.2s 首字」

### 探针缺陷备案（避免再踩）

- `238z` 的 B/C 组用 `sections(i)` / `plan_block(i)`（`i` = 轮次）**人为制造每轮变化**
  ⇒ 结论只对「确实每轮变」的场景成立，**而真实场景不是**
- `238aa` 的 G2/G3 把「变化」写成**每次相同的常量**（`"（v2）"`、`"轮次标记：now"`）
  ⇒ 连发 3 次后自己也被缓存 ⇒ G3 的 `cached=4096` 是**假命中**（当轮即被 `238ab` 推翻）
- `238ab` 首版连跑 3 次 `asyncio.run` ⇒ 连接池随首个事件循环关闭失效 ⇒ 两次都「0 段」
  ⇒ 差点得出「sections 两次相同」的**假结论**（方向碰对了，但当时数据不可用）

### 由此得出的行动建议（修正第五节 / 第八节）

1. **不建议**为 sections / plan_block 的「挪位」动生产代码：真实收益是**偶发的一次 messages 段重算**，
   而挪位需要过语义保真验证（system 里的内容 vs 消息里的内容，模型权重不同）⇒ **投入产出不划算**。
2. **若要量化真实收益**，先量「多轮任务里 todo 实际变动几次」——那才是触发次数。
3. **砍工具的评估不受影响**，但收益口径改为「省输入计费」。
