# 第 300 轮 · 风险识别耗时 —— 分层方案（**已落地并实测**）

> 老板第 3 条征询：「仅 20 条评论就要风险识别非常久，不符合实际。是否需要设置分层的风险识别还是其他做法」
> 老板后续指令：「选D的话会犯你之前说的以前犯过的错吗？如果不会则执行ABCD」
> **状态：A / B(不做) / C / D 已落地**；判决与实测读数见下。

---

## 零、落地结果（一句话 + 数字）

| 档 | 20 条耗时 | 说明 |
|---|---|---|
| 浅层（规则，**默认**） | 2.9 ms | 零模型成本；`deep` 默认 `False` |
| 深层（分层 + 批量）**实测 19 条 1.18 ~ 1.44 s** | **↓ 36.7×** | 对照第 299 轮真机 43.4 s |

**分层三步**（`service.scan_reviews_risk` 的 deep 分支）：

```
① 规则通道**全量**先跑（0.15 ms/条）→ 它同时决定「谁不用送语义」
② rule.risk_categories 非空 ⇒ **不再送语义**（D）
③ 其余条目**打包成一次批量语义调用**（C），按序号回填
```

**质量（72 条评测集：`r299_risk_eval_set.json` 48 + `holdout` 24）**

| 量 | 读数 |
|---|---|
| 只用规则通道 | P 1.00 / R 0.636 / F1 0.778（**漏 12 条**） |
| **分层（规则 + 批量语义，6.1 s）** | **P 1.00 / R 1.00 / F1 1.00** |
| 规则未命中子集（51 条）上的批量语义 | P/R/F1 **1.00**，12/12 正类全抓到、0 误报 |
| 同一子集用**逐条**参照实现（87.8 s） | P/R/F1 1.00 ⇒ 批量**14.8×** 且质量不降 |

★ 演示集（19 条）的 12 条正类**全被规则命中**，所以「端到端 1.00」只由规则背书；
上面的评测集才是唯一检验语义通道的地方 —— 详见 §六。

## 一、把「非常久」拆成可归因的数字（第 299 轮的原始归因）

| 问题 | 结论 |
|---|---|
| 慢在哪一步？ | **逐条串行调用 LLM**，不是取数、不是规则、不是排序 |
| 单条多慢？ | **2.70 ~ 2.81 s / 条**（实测） |
| 20 条多慢？ | **43.4 s**（上一轮真机读数） |
| 慢在「条数」还是别处？ | ★ **判据是输出 token 量，不是条数**。同样 19 条，把输出从「带理由」压成「只回类别码」，**20.9 s → 6.14 s** |

## 二、D 的安全性判决（老板那一问的直接答案）

问：「选 D 的话会犯你之前说的以前犯过的错吗？」

**答：宽泛版会，收紧版不会。** 判决探针 `.workbuddy/probes/r300_risk_layers/decide_d_safety.py`
（7 样本 × 4 种 LLM 出口 = 28 格）：

```
[1] D-宽泛（rule.categories 非空即跳过）  改变 decision 的格子数：3
    T_EMOTION llm=unknown   unknown -> clean
    T_EMOTION llm=hit_r3    risk    -> clean     ← 漏报
    T_EMOTION llm=hit_r3r4  risk    -> clean     ← 漏报
[2] D-收紧（rule.risk_categories 非空才跳过）  改变 decision 的格子数：0
```

**机制级理由（这才是「为什么」）**：`fuse()` 在 `merged.risk_categories` 非空时
**提前 return**、压根不读 LLM 的 decision ⇒ 四类命中时「不送语义」是**无操作**。
而**只命中 r5**（高情绪）时规则判 `CLEAN`、`fuse()` **要**读 LLM 的结论
（LLM 可能报 risk）⇒ 把它也短路掉就是**让下游通道零参与** ——
与第 246 轮「关键词短路抢在技能注入之前 `return`」**同构**。

⇒ **硬约束：短路条件必须是 `rule.risk_categories`，不许写成 `rule.categories`。**
已用 AST 门禁 + 反向注入双重钉死（§七）。

### 批量协议（压缩输出的三态必须齐）

```
输入： [{"n": 1, "text": "..."}]                    ← 用**序号**不用 review id（模型复述长 id 会错）
输出： {"1": "", "2": "?", "3": "r2:high|原文逐字片段"}

  ""       ⇒ clean   （模型明确判无风险）
  "?"      ⇒ unknown （模型拿不准 —— 与 clean **方向相反**，不可合并）
  "cat:level|证据" ⇒ 命中；证据必须能回到原文（`_is_grounded`，与逐条版同一条铁律）
```

- **缺项 / 解析失败 / 调用异常 ⇒ 一律 `unknown`**（fail-closed），绝不猜 `clean`。
- `max_tokens` **逐次**随条数放大：`get_llm()` 按模型名缓存单例，建实例后再传参数**无效**。
- 拆包上限 `RISK_SCAN_BATCH_CHUNK = 10`（换**失败半径**，不是为了省钱），多包**并发**发。
- 兼容 4 种模型常见的返回形态（裸映射 / `{"items":{...}}` / 列表 / **逐条版对象**）——
  只认一种就会把「格式不合我意」记成「模型判不出来」，归因方向错。

## 四、关键约束（第 299 轮列出的，本轮仍有效）

| # | 约束 | 影响 |
|---|---|---|
| 1 | `fuse()` docstring 写着「规则命中不阻止 LLM 判定」，防的是「**关键词没命中就当干净**」＝漏报 | ⇒ 跳过「**已命中**」不构成那个坑；跳过「**未命中**」才是重犯。**方向不可反** |
| 2 | `get_llm()` 按模型名缓存单例，`max_tokens` 只在建实例那次生效 | ⇒ 批量必须把 `max_tokens` 作 per-call 参数，否则输出被**静默截断** |
| 3 | 批量会出现 **2~4 条「过度并列」**类别码（如 `r2 → r2,r4`） | ⇒ 二分类不变，逐类精度会掉；前端展示类别需接受噪声 |
| 5 | 前端全局 `timeout: 30000`，deep 靠 per-call 兜住 | ⇒ 门禁 R12 现在按「≥ 全局值 ×3」判，不再硬编码 |
| 6 | **压缩输出丢 `unknown` / `clean` 的区分** | ⇒ 必须补 `?` 信号，否则「拿不准」被静默洗白成「干净」（本仓最忌讳的静默退化） |

## 五、为什么不选 B（后台异步）

B（点完立刻返回 + 轮询/SSE 回填）**不降总耗时**，只改观感，但需要任务态存储 + 轮询。
分层之后总耗时已经降到约 1.2 s —— **等 1 秒**不值得引入一套任务状态机。
⇒ B 保留为「将来条数上调到几百条时」的候选，本轮不做。

## 六、已知口径差异与遗留项（**如实记在案**）

### 6.1 批量版用 `clean` 的地方，逐条版常给 `unknown`（**已确认，非抖动**）

72 条评测集上，51 条送语义的样本里 **14 条 decision 不一致**，全部是
`逐条=unknown → 批量=clean`，**没有一条是「批量漏掉 risk」**。
反复跑两轮稳定复现。三个例子（gold 全为 `none`，批量判 clean 是**正确**方向）：

- `Colour is darker than the photos ... Not a deal breaker, just something to know`
- `Seal gave up after a month ... Everything else about it still works`
- `Runs small, otherwise fine ... Three stars for the build`

⇒ **影响**：界面上的「未定论 N」会**变小**。这是**提示词形态效应**（逐条版让模型更容易
说自己「拿不准」），不是判定能力变化。好处是人工复核队列变短，代价是
**「未定论」这个数字不能跨版本比较**（第 299 轮的 3 条 vs 第 300 轮的 0 条）。
⇒ 已写进 `scan_llm_batch` 的 docstring；**没有**用门禁去钉死它 —— 它依赖模型行为，
离线门禁钉不住，只能靠这里的读数留痕。

### 6.2 演示集（19 条）**不能**用来检验语义通道

演示集的 12 条正类**全部被规则通道命中** ⇒ 走分层后它们根本不进语义通道。
「端到端 P/R/F1 = 1.00」因此只由规则背书。**必须**用
`scripts/data/r299_risk_eval_set.json` + `holdout`（72 条、含 12 条「只有语义能救」的正类）
来量 —— 见 §零。

### 6.3 两条提示词**同补**了陷阱规则（实测有效）

复测中发现批量版在两条「叙述式/建议式」陷阱上误报：
`You have to escalate this to tier 2 support`（给别人的建议）、
`I filed a warranty claim ... they sent a new lid`（已解决的过去时叙述）。
两条提示词都补上这两条反例后：

| | 补之前 | 补之后 |
|---|---|---|
| 未命中子集 P/R/F1 | 0.857 / 1.00 / 0.923（2 误报） | **1.00 / 1.00 / 1.00**（0 误报） |

★ 只在批量版补而不补单条版 = 「同一判定两份口径」，所以**两边一起改**（收敛唯一真源）。

### 6.4 待测未知量

- 真实（非演示）数据上的「规则未命中占比」p：评测集上 51/72 ≈ 71%。
  p 越大，语义通道的成本越接近批量全量的 6.1 s；p 越小，越接近浅层的毫秒级。
- `RISK_SCAN_BATCH_CHUNK = 10` 是拍的（失败半径 vs 固定开销的折中）。
  拆包只在 >10 条时生效，deep 上限 20 ⇒ 最多 2 包并发。

## 八、附：为什么「deep 只花 1.2 s 也算值得」

第 299 轮的既有事实：同一份 gold 上，深扫对「要不要报警」增益为 0
（12 条正类规则全抓到），只换来「3 条 none 变未定论」+ 逐类精度下降（r2/r4 = 0.60）。

⇒ 所以本轮**先把它变便宜**（43.4 s → 1.2 s，36.7×），再谈「值不值」。
变便宜之后，「该不该默认深扫」才是一个可以重新讨论的问题 —— 而**不是**现在改默认值：
A 档的口径是「默认浅层，语义只在用户按按钮时发生」，这一条已经用门禁钉住。
