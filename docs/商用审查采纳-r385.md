## 三、A2 演示种子守卫：不让演示数据进客户店铺

### 缺陷形态

`modules/products/seed.py:359` 的守卫是「**全表**（`spus`）为空 ⇒ 给**每个**
已存在店铺灌一份」。触发条件很具体：

> 全新库 + 客户已建店 + 客户还没录产品 + 重启一次 ⇒ **演示商品被灌进真实店铺**。

`wiring.SEED_STEPS` 里同类步骤共 **11 个**（products / assets / candidates /
monitors / competitor_snapshots / platform_rules / knowledge_base / skills /
trade / market_snapshots / demo_store）。

★ 其中 `platform_rules` / `knowledge_base` 一度被我认为是"产品内置通用内容，
可以给真实客户"——**读内容后否掉了这个判断**：规则写的是「Amazon 标题最多
200 字符」这种**编造的政策**，话术写的是「30 天内可申请退货」这种**编造的
店铺政策**。二者都会让客户照着错的规则改 Listing。⇒ 一律 demo only。

### 改法

- `core.bootstrap.SeedStep` 加 `requires_demo: bool = False`；
- `seed_base_data(steps, *, demo_mode=None)` 在非 demo 模式下**跳过**这些步骤
  （**记 0 条、不删键** —— 键少一个会被 CI/探针读成"这一步不存在"）；
- 默认值运行期读 `config.demo_mode`（不是 import 期固化，否则「改 .env 再重启」失效）；
- `wiring.SEED_STEPS` **11 个步骤**显式标 `requires_demo=True`，`plans` 保持不标
  （套餐缺了注册接口直接 500，绝不能跟着 demo 开关走）。

### 判据

`tests/test_seed_demo_guard.py`（6 条）：
非 demo 跳过 · demo 全跑 · 跳过时键集合不变 · 默认读 config ·
**清单型判据**（`MUST_BE_DEMO_ONLY` 11 个必须标）· `plans` 永不标。

**反向注入 2/2 抓到**（`mutate-seed-demo-guard.py`，改前算 sha256、`finally` 还原并复核）。

### 顺带修的既有红（非本轮引入）

`test_core_internal_layering.py::test_standalone_units_registry_is_exact` 一直红：
`core/money.py` 自第 378 轮「金额改分」起就没登记进 `STANDALONE_UNITS`。
本轮按该文件自己写的处理方式**补登记 + 写清理由**（纯换算内核，零 core 依赖）。

## 四、B1 档位上闸：让 ¥999 有理由存在

### 缺陷形态

`max_shops` / `max_users` 在 `subscription_plans` 里是 3/1、10/5、50/20，
全仓只有两处读、且都是**展示**：

```
modules/billing/router.py:159-160
modules/secretary/subscription_tools.py:112
```

⇒ 免费版能建 50 家店、能加 20 个人。对比 `api_calls` / `agent_chat` 是真上闸的
（`main.py:502 API_QUOTA`，22 处消费）—— 这是"做了一半"。

### 改法

新模块 `modules/billing/plan_limits.py`：

```
get_plan_limits(db, user_id)        取生效订阅档位；无订阅 ⇒ FREE_FALLBACK（3/1）
count_account_shops / count_account_seats   席位 = 1(owner) + 成员数
enforce_account_limit(db, account_id, metric)   超限抛 402 + 结构化 detail
```

接入点（**两处都改**，只改一处等于只挡一半）：

| 端点 | 维度 |
|---|---|
| `modules/stores/router.py::create_store` | `max_shops` |
| `core/auth/accounts_router.py::invite_member` | `max_users` |

三条设计决定：

1. **按账户所有者的订阅判档**（套餐是"这个团队买了什么"，不是"操作者买了什么"）；
2. **没有生效订阅 ⇒ 按免费版上限**（不是放行 —— 取不到就放行会把闸变摆设）；
3. **不加行锁**（试过，会自死锁，见下）。

### 踩到的坑（留档）

第一版在 `enforce_account_limit` 里对 `accounts` 行加了 `SELECT ... FOR UPDATE`。
`test_stores.py` **整组挂死**（22 秒 → 卡死超时）。根因不在档位闸，在既有的
**双 session 写入**：`create_store` 的 `_upsert_store_db()` 用**另一个** session，
它插 `stores_store` 时 PG 要对被引用的 `accounts` 行加 `FOR KEY SHARE` 做外键检查
—— 而我们正持有同一行的 `FOR UPDATE` ⇒ **同一请求内自死锁**。

⇒ 去掉行锁，接受一个**有界**的 TOCTOU（并发建店最多多出 = 并发数，下一次请求
读到真实行数就拒），并在 docstring 里写明「彻底解法是把 `_upsert_store_db`
收进同一 session，属独立改造」。

### 前端

`src/api/request.ts` 加 `case 402`（原来会掉进 `default`，把**结构化 detail 对象**
直接喂给 `message.error` ⇒ 用户看到 `[object Object]`，比没提示更像崩溃），
并抽出 `detailText()` 归一化 detail；`default` 分支同步改用它。

### 判据

`tests/test_plan_limits.py`（11 条）：兜底值 · **与 `init_default_plans` 的 free 档对账** ·
无订阅/失效/生效三态 · 边界 `current >= max` · 402 错误体可 JSON 序列化 ·
**AST 接线判据**（`create_store` / `invite_member` 真的调了闸门 —— 防"模块写好了但没人调用"）。

### 测试适配

`test_account_store_hierarchy.py` 两个用例原本用免费档邀请成员，
上闸后 402。**产品语义正确**（免费版 1 席 = 只有你自己），因此在用例里补
`_promote_to_pro()` 而不是放松门禁 —— 它们验的是角色矩阵，不是计费口径。

## 五、B2 退款登记：让 `refunded` 不再是死枚举

### 缺陷形态

`Invoice.status` 注释列着 `refunded`，全仓**无任何写入路径**
（`grep -rn refund backend/modules/billing/*.py` 只命中注释与两处"矛盾状态
不许静默开权限"的判断）⇒ 客户要退款时系统里无法表达，运营只能改 SQL，
对账/客服/发票三条线都看不到痕迹。

### ★ 边界：这是**登记**，不是打款

本项目**没有支付宝商户号**，`alipay.trade.refund` 的真实报文无法验证。
写一条没人验证过的**资金调用**比不写更危险 —— 它会让人以为"点了就退了"。

⇒ 语义明确为：**运营在支付宝后台退完钱，回系统登记**。响应体里带：
`"note": "已在系统内登记退款；资金退还需在支付宝商户后台完成（本接口不发起真实退款）。"`

### 改法

| 层 | 内容 |
|---|---|
| 模型 | `invoices` 加 `refunded_at` / `refund_reason` / `refund_operator_id`（不建外键：操作人删号不该带走账单） |
| 迁移 | `alembic/versions/o1c8e5a3d9f2_invoice_refunds.py`（幂等：先 `inspect` 再 `add_column`） |
| 唯一入口 | `payments.refund_invoice()`：行锁 + 状态判定 + 幂等 + 顺带撤销订阅 |
| 端点 | `POST /api/v1/billing/invoices/{id}/refund`（**平台超管**）→ 404 / 409 / 200 |
| 列表 | `GET /invoices` 返回 `refunded_at` / `refund_reason` |

**为什么放 `payments.py` 而不是端点里就地改**：`invoices.status` 的写入点必须收敛
—— 现在只有两处（`settle_invoice` → paid、`refund_invoice` → refunded）。
这条由 `test_only_two_status_writers`（AST）钉住。

### 判据

`tests/test_billing_refund.py`（9 条）：三列落库 · 订阅撤销 · 幂等且不二次撤销 ·
pending 拒退 · 不存在 · `revoke_subscription=False` · 非超管 403 · 超管 200 · 409/404 ·
**AST：端点挂 `get_admin_user`** · **AST：状态写入点只有两处**。

**反向注入 2/2 抓到**（`mutate-billing-refund.py`）。

## 六、没做的（如实列）

### C「按店取数」—— 本轮刻意不做

审查员 P0-1 的修法写的是「3~5 天纯接线」，**低估了**：

- `SPAPIClientAuth` 是**同步单例 + 进程级 token 缓存**；
- 数据源内部用 `ThreadPoolExecutor + asyncio.run` 桥接同步接口；
- 按店构造要在**同步栈里读 DB + 解密凭据**，还要解决实例生命周期（按店缓存/失效）。

估 **5~8 天**，且必须独立开一轮。改造清单（下一轮的输入）：

| # | 动作 | 为什么必须这一条 |
|---|---|---|
| 1 | `SPAPIClientAuth` 支持 `from_store(credentials)` 构造 | 现状只从进程 settings 读一个全局 refresh_token |
| 2 | 新增凭据提供者：按 `store_id` 读 `amazon_credentials` + 解密 + 进程内缓存（过期前 5 分钟刷新） | oauth 已按店落库（`router.py:112/301`），但没人读 |
| 3 | `is_available()` 改为「**该店**有 ACTIVE 凭据」 | 现在判的是「本进程配了一个卖家」 |
| 4 | 数据源内所有 `fetch_*(store_id, …)` 用该店 auth | 现状：`store_id` 收了**全程不用**（`sp_api_source.py:217-250`） |
| 5 | 同步栈取凭据的形态要定：工厂在 async 上下文预取后传给同步实例（推荐），或在同步栈里 `run_coroutine_threadsafe` | 这一条决定了改动量级 |
| 6 | **该店无凭据 ⇒ 显式报错，禁止回退 mock** | 回退 mock = 继续用编造数据冒充真实（本仓铁律：取不到禁静默退化） |
| 7 | `product_research` 改走 `amazon_sp` 数据源 | 选品现在整条链走 `AmazonAdapter`，9 处 `_warn_mock` |
| 8 | 竞品快照加真实同步任务 | 现在唯一写入点是 `amazon_sp/seed.py:155`，**没有同步任务** |
| 9 | 验收判据：两租户各接一个卖家 ⇒ **互相看不到对方数据**；无凭据时显式报错 | 这是"能收第一笔钱"的唯一硬判据 |

★ 顺带发现两条报告没写到的：

1. **`fetch_daily_sales(store_id, …)` 收了 `store_id` 全程不用**
   （`sp_api_source.py:217-250`；广告侧 `agent_ad.py:134` 传进去同样白传）
   —— 比"全局单例"三层推理更直接的一行证据。
2. **竞品监控也是编造数据，且比选品更隐蔽**：`CompetitorSnapshot` 全仓唯一
   写入点是 `amazon_sp/seed.py:155`，**没有任何真实同步任务**；它不在
   `_warn_mock` 名单里，所以连一条 warning 都没有。
