## 二、数据现实（第 299 轮实测，先看这个再谈算法）

脚本 `backend/scripts/probe_r299_review_inventory.py`（只读）读数：

| 读数 | 值 |
|---|---|
| `customer_reviews` 总行数 | **4** |
| 店铺数 / SKU 数 / ASIN 数 | 1 / 1 / 1（`store_c3529ab1`，amazon） |
| rating 分布 | 1★ ×1、2★ ×2、5★ ×1 |
| `status` | 全为 `triaged` |
| `source` | 全为 `mock_seed`（**没有一行来自真实平台**） |
| 四类风险话术粗筛命中 | 威胁 **0** / 索赔 **1**（且是假阳性）/ A-to-Z **0** / 开 case **0** |

**结论（必须先说）**：库里的 4 条评论主题**全是「物流慢 + 包装压坏」**，
**四类风险话术一条正样本都没有**。

⇒ 「拿现有数据跑一遍看效果」这条路**在这批数据上跑不出效果**：
命中的 1 条还是假阳性 —— 原文 `Replacement foam inside was too thin`
说的是「替换用的泡沫太薄」，与索赔无关，纯关键词通道把它当成了「要 replacement」。

**这也顺带给出了第一个实证**：`replacement` / `case` / `refund` 这类词
在评论里的**默认语义不是风险**。⇒ 纯关键词通道的误报率在本域不可接受，
语义判定不是可选项而是必需项。

**因此 P0 的效果证明方式改为**：用**独立构造的评测集**（§五）测算法准不准，
用**库内真数据**测「真数据上会输出什么」。两者分开报，不混为一谈。

## 三、四类风险的判定口径

★ 口径的总原则（对齐本仓既有判据）：
1. **每条判定必须给得出证据片段**（原文里的一段连续文本）。给不出证据的判定 =
   一句读后感，等同没有判定。
2. **判不了就标 `unknown`**（fail-closed），不得静默当「无风险」。
3. **「写了什么」与「想干什么」分开判**：`refund` 出现在「谢谢你痛快退款」
   里是**叙述**；出现在「不退款我就去亚马逊投诉」里才是**施压**。
   区别不在关键词，在**条件句/威胁结构**。

### R1 · 威胁差评（threat_to_review）

| 项 | 内容 |
|---|---|
| 定义 | 以「公开负面评价 / 社交曝光 / 让其他人别买」为筹码，要求卖家让步（或纯粹泄愤预告） |
| 正例特征 | 条件句结构：**若不 X，我就 Y**（Y = 差评/曝光/劝退） |
| 正例 | 「**If** you don't refund me **I'll leave a 1-star review** on every listing.」 |
| 反例（陷阱） | 「I returned it and **left a review** — happy to say it was 5 stars.」（叙述已发生的正面评价） |
| 反例（陷阱） | 「**Reading other reviews** helped me pick the right size.」（reviews 是别人写的） |
| 证据要求 | 必须截出**条件句两个半句**（威胁条件 + 威胁动作） |

### R2 · 索赔 / 要钱（claim_compensation）

| 项 | 内容 |
|---|---|
| 定义 | 明确提出金钱或等价物要求（退款 / 补偿 / 赔偿 / 差价 / 折价券），且**带施压或最后通牒** |
| 正例 | 「The unit arrived cracked. **I want a full refund and compensation for the time I wasted**, or I'm contacting consumer protection.」 |
| 反例（陷阱） | 「**Replacement foam inside was too thin**.」（replacement 是配件，不是索赔诉求）—— 本库真实误报 |
| 反例（陷阱） | 「Quick **refund**, no questions asked. Five stars.」（正面叙述流程） |
| 反例（陷阱） | 「I **returned** it because the size was wrong.」（正常退货，无施压） |
| 证据要求 | 必须同时截出**诉求**与**施压/最后通牒**（缺施压 ⇒ 降级为 R5 普通售后诉求） |

### R3 · A-to-Z 索赔前兆（a_to_z_precursor）

| 项 | 内容 |
|---|---|
| 定义 | 提及或即将触发平台担保索赔（Amazon A-to-Z Guarantee / 平台先行赔付） |
| 正例 | 「I've waited 3 weeks. **I'm filing an A-to-Z claim** tomorrow.」 |
| 前兆形态（无明说，但语义等价） | 「I'll just **let Amazon handle it** and get my money back.」 |
| 反例（陷阱） | 「Amazon's **A-to-Z Guarantee** is why I trust shopping here.」（正面提及政策名） |
| 反例（陷阱） | 「The seller resolved it **before it ever got to A-to-Z**.」（叙述已解决） |
| 证据要求 | 截出**触发意图**所在的句子；仅出现政策名不算命中 |

### R4 · 开 case / 投诉平台（open_case_precursor）

| 项 | 内容 |
|---|---|
| 定义 | 以「向平台/第三方/监管投诉、升级、举报」为筹码或预告 |
| 正例 | 「**I'm opening a case with Seller Performance** and reporting this listing.」 |
| 正例 | 「**Escalating to Amazon support** unless someone replies today.」 |
| 反例（陷阱） | 「**In case** you're wondering, the color is more teal.」（in case 是连词） |
| 反例（陷阱） | 「The **case** itself is sturdy.」（case = 外壳/保护套） |
| 反例（陷阱） | 「Their support **case** got closed quickly.」（叙述历史工单，已完成） |
| 证据要求 | 截出**升级对象 + 动作**（平台名 / 监管方 + 投诉/举报/升级动词） |

### R5（辅助档，不是老板点名的四类）· 高情绪差评（不含威胁）

不带任何威胁结构、但情绪强度极高的差评（`furious` / `scam` / `never again` /
全大写）——**它是预警的候选池**，本身不是「风险话术」。
单独列出来，避免它与 R1~R4 混在一个数字里被误读。

## 四、等级与建议动作

| 等级 | 判据（满足其一） | 建议动作（**仅建议，不自动执行**） |
|---|---|---|
| `high` | 命中 R1/R3/R4 任一类，或 R2 带明确最后通牒 | 立即人工介入：优先处置 + 走 `review_dispositions` 的 `proposed` |
| `medium` | 命中 R2（有诉求、施压弱），或多类弱信号叠加 | 24h 内人工确认 |
| `low` | 仅 R5（高情绪、无威胁） | 进候选池，批量看 |
| `unknown` | 文本过短 / 语言不支持 / 语义歧义 | **显式列出待人工判**，不计入「无风险」 |

★ **等级与动作分列**：等级是「文本判成什么」，动作是「人该做什么」。
把两者合成一个字段，将来改动作口径就得动判定逻辑（本项目踩过这类坑）。

## 五、评测集设计（★ 独立于规则模式串）

★ 为什么必须独立：如果我**先写模式串、再照模式串写样本**，那是自我循环 ——
准确率恒等于 100%，证明不了任何事。

设计约束：
1. 样本**先用自然语言写成**（像真实买家），**不回头看模式串**；
2. 正样本的措辞**故意不与模式串逐字对应**（例如模式串有 `leave a review`，
   样本写的是 `I'll make sure everyone on Reddit hears about this`）；
3. 负样本**专挑最容易误报的形态**（§三 每类都列了陷阱）；
4. 库内 4 条真实 mock **全部纳入评测集**（作为负样本，因为它们确实无威胁）。

样本规模：正样本 ≥ 20（四类各 ≥ 5），负样本 ≥ 20（含全部陷阱类型），
合计 ≥ 40。每条带人工标签（`label` ∈ {r1,r2,r3,r4,none} + `level`）。

## 六、指标口径

| 指标 | 算法 | 说明 |
|---|---|---|
| 逐条命中率 | 命中条数 / 总条数 | 单看它无意义（判全命中也能 100%） |
| **精确率 P** | 真命中 / 全部命中 | 决定「打扰率」 |
| **召回率 R** | 真命中 / 真实正样本数 | 决定「漏报率」 |
| F1 | 2PR/(P+R) | 综合 |
| **误报原文** | 逐条列出 | ★ 必须给老板看原文，由老板判「这算不算误报」 |

★ 单类指标分开报，**不给一个总分** —— 四类里 R1（威胁）漏报代价远高于
R3（A-to-Z 前兆），合成一个 F1 会把这个差别抹平。

## 七、三条通道与融合（★ 实测后改过一次，见 §九）

| 通道 | 做什么 | 为什么需要 | 进融合？ |
|---|---|---|---|
| **naive** 朴素关键词 | 一个词表，命中即报 | **反面基线**：它就是「用关键词做风控」这条路真实的样子 | **否** |
| **rule** 结构化规则 | 要求「筹码/诉求」+「施压/条件结构」 | 零成本、可解释、可复核 | 是 |
| **llm** 语义判定 | 四类 + 等级 + 证据片段 | 处理「词不在但语义在」以及 §三 那些陷阱 | 是 |
| **fuse** 融合 | 规则 ∪ LLM；同级冲突取**等级高者**，两侧证据都留 | 给老板一个数字 | — |

★ **为什么不是「规则优先、LLM 兜底」**：本仓踩过「关键词短路早于语义」的坑
（点名技能永不生效）。规则命中**不阻止** LLM 判定，反之亦然。

★★ **为什么 naive 被排除在融合之外**（首版实现把它放进去了，实测后果很重）：
融合是并集 ⇒ **一条坏通道会污染好通道**。实测时库里那条 5 星好评
`Exactly as described, arrived early, no complaints at all` 被朴素关键词判成
「开 case 投诉 / high」；并集之后 LLM 的正确判定被盖掉，**最终报警里混进一条五星好评**。
⇒ 拒绝名单写在 `fuse()` 内部（不靠调用方自觉），没有「谁记得就别传」的空间。

| 档 | 内容 | 卡点 |
|---|---|---|
| P1 | 把识别结果落成只读视图 + 前端「标红置顶」 | 无卡点，纯前端 + 一个读端点 |

等通道通了直接复用。

## 九、实测读数（第 299 轮实跑，脚本 + 原始输出都在仓里）

复现：
```
cd backend
python scripts/probe_r299_review_inventory.py   # 盘点数据
python scripts/probe_r299_risk_eval.py          # 三通道评测 + 库内实跑
```
原始输出：`backend/out-probe-r299-review-inventory.txt` / `out-probe-r299-risk-eval.txt`

### 9.1 开发集（48 条：正 21 / 负 27）—— 规则在此收敛，**有调参泄漏**

| 通道 | TP | FP | FN | TN | 精确率 | 召回率 | F1 | 未定论 |
|---|---|---|---|---|---|---|---|---|
| naive 朴素关键词 | 12 | 18 | 9 | 9 | 40.0% | 57.1% | 47.1% | 0 |
| rule 结构化规则 | 21 | 0 | 0 | 27 | **100.0%** | **100.0%** | 100.0% | 0 |
| llm 语义 | 21 | 1 | 0 | 26 | 95.5% | 100.0% | 97.7% | 14 |
| fuse 融合（rule ∪ llm） | 21 | 1 | 0 | 26 | 95.5% | 100.0% | 97.7% | 13 |

### 9.2 holdout（24 条：正 12 / 负 12）—— 规则**冻结后**新写，换措辞

| 通道 | TP | FP | FN | TN | 精确率 | 召回率 | F1 | 未定论 |
|---|---|---|---|---|---|---|---|---|
| naive 朴素关键词 | 4 | 9 | 8 | 3 | 30.8% | 33.3% | 32.0% | 0 |
| rule 结构化规则 | 0 | 0 | 12 | 12 | n/a | **0.0%** | n/a | 0 |
| llm 语义 | 12 | 0 | 0 | 12 | **100.0%** | **100.0%** | **100.0%** | 10 |
| fuse 融合 | 12 | 0 | 0 | 12 | 100.0% | 100.0% | 100.0% | 10 |

**三条可执行的结论：**

1. **关键词风控不可行**：朴素通道精确率 30~40% ⇒ 每 3 条报警里 2 条是假的。
   它误报的正是最不该误报的：`in case`（连词）、`the hard case`（外壳）、
   `A-to-Z Guarantee 是我在这买东西的原因`（正面提及）、
   `Exactly as described, no complaints`（五星好评被判成「开 case/high」）。
2. **规则通道没有可证实的价值**：开发集 100%/100% 完全来自调参；
   换一批**真实风格**的措辞后召回 **0%**。它命中的，LLM 全都命中；它漏的，LLM 都能补。
   ⇒ 融合结果 = LLM 结果，规则**零增量**。
3. **LLM 通道可用**：holdout 上 100%/100%，且类别全部判对
   （含 H07「绕开卖家走平台退钱」这种**没点名 A-to-Z 但语义等价**的形态）。
   另有 9~14 条判「未定论」——全都是负样本，即**拿不准就不报**，fail-closed 生效。

★ 一个必须说明的**公平性限制**：holdout 的 12 条正样本是我**刻意避开常见威胁词**写的，
所以它对规则通道偏不利。真实评论里会有一部分含明显词汇（`leave a negative review`），
规则对那部分仍能命中。**但方向是明确的**：规则不能作为可靠性来源，
真实命中率介于 100%（开发集）与 0%（holdout）之间，且**不可控**。

### 9.3 库内真数据（4 条，只读）

| 评论 | 朴素 | 规则 | LLM | 融合 |
|---|---|---|---|---|
| 1★ Twelve days and the box was destroyed | clean | clean | r5 高情绪 | r5 |
| 2★ Arrived crushed again | r1+r2 **误报** | clean | r5 高情绪 | r5 |

## 十、本次踩到的四个坑（都已在代码里修掉，留档防复发）

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 1 | **评测集污染** | 边看误报边调规则 ⇒ 开发集冲到 100%/100%，换集即 0% | 分「开发集 / holdout」，且**先写样本再写规则**；报告里明确标注哪份有泄漏 |
| 2 | **R2 门槛实现与文档不一致** | 文档写「缺施压 ⇒ 降级」，代码写「缺施压 ⇒ 报 medium」⇒ 4 条叙述式误报（`refund showed up` / `no damage` / `they offered compensation`） | 四类**门槛各不相同**写进 docstring；引入「要求式 vs 叙述式」判别 |
| 3 | **「无风险」与「未定论」混成一个数** | LLM 明确判无风险也记成 `unknown` ⇒ 报告里「未定论」列变成「无风险」的同义词，两个方向相反的结论合成一个数 | `ScanResult.decision` 显式三态：`risk` / `clean` / `unknown` |
| 4 | **坏通道污染好通道** | 融合取并集 ⇒ 朴素通道把五星好评判成 high，盖掉 LLM 的正确判定 | `fuse()` 内部**拒绝名单**（不靠调用方自觉）排除 naive |

★ 坑 3 与坑 4 的共同点：**两个方向相反的语义被合成一个字段**。
本仓既有判据「三态不可压成两态」在这次实操里又命中一次。
