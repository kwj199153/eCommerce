## 结论先行

1. **这不是「多租户还没做」，是「真实数据通路从来没跑通过」。** 即便只有一家店、`.env` 里凭据完全正确，`SpApiDataSource` 照样在第一次调用时抛 `REFRESH_TOKEN_MISSING` —— 它把一份**空配置**传给了客户端，而真正带凭据的那个 auth 实例**赋值后再也没被用过**。
2. 所以本轮的真正目标不是「加多店支持」，而是**把 `凭据 → 配置 → 客户端 → 调用点` 这条链接上**，顺手让它按店工作。
3. 工程量 **5~6 天**（不是报告说的 3~5）。不改表、零迁移。

## 一、缺陷形态：链在四个地方断了

### 1.1 配置注入断链（单店也不通的根因）

```python
# modules/amazon_sp/data_sources/sp_api_source.py:71-81
self._config = config or SPAPIConfig()        # ← 空配置：lwa.refresh_token == ""
self._client = SPAPIClient(self._config, ...) # ← client 拿空配置自建 auth
self._auth   = get_spapi_auth()               # ← 带环境的那个，赋值后再也没用过
```

`SPAPIClient` 的判断是 `SPAPIClientAuth(config) if config else get_spapi_auth()`，
而空的 `SPAPIConfig()` 是**真值**（dataclass 无 `__bool__`）⇒ 走了「自建」，永远不走单例。

实测（`./.venv/Scripts/python.exe`，无网络调用）：

| 断言 | 结果 |
|---|---|
| `src._client.auth is src._auth` | **False**（各是一个实例） |
| `src._client.auth.config.lwa.refresh_token` 为空 | **True** |
| `src._auth` 的 refresh_token 为空 | False（读的是 `.env` 占位符） |
| 工厂返回类型 | `MockAmazonDataSource` |

⇒ 第一次 `get_access_token()` 就在 `auth.py:207` 抛 `REFRESH_TOKEN_MISSING`。
**这条路径从来没有产出过一条真实数据**，只是被 mock 回退挡住了，所以没人发现。

### 1.2 凭据不进数据源

| 位置 | 形态 |
|---|---|
| `fetch_credentials(store_id)` | 名字叫「取凭据」，实现里**不查表**，把 settings 拼一条记录返回，`refresh_token` 写死 `"***"` |
| `fetch_daily_sales(store_id, …)` | `store_id` 全程只出现两次：签名、给结果行打标签（L218 / L266） |

⇒ 数据是谁的都行，只要最后打上 `store_id` 标签。

### 1.3 工厂没有「店」这个概念

`get_data_source(prefer="auto")` 无 `store_id` 形参；`is_available()` 是 classmethod 读全局 `settings`。
全仓 0 处给工厂传过 `config`。

### 1.4 两套按店凭据存储，没有优先级规则

| 通道 | 表 | 状态 | 入口 |
|---|---|---|---|
| **表单直填** | `stores_store.api_credentials`（Fernet 密文，`enc:v1:`） | 真实可用：连接时**真调过一次 SP-API 只读探针**并落库 | `POST /stores/{id}/connect`，有 UI |
| **OAuth 授权** | `amazon_credentials`（token 逐值密封） | 写侧完整：状态机 / `error_count` / 刷新端点；但**连接流程不写它**，也没有 UI 入口 | `/amazon-sp/*` 端点 |

两条通道都「合法」，但取数时**一条都没读**。

### 1.5 类型不一致（现在没暴露，接上就炸）

`stores_store.id` 是 `String(64)`（形如 `store_xxx`），而接口签名是 `fetch_daily_sales(store_id: int, …)`。
现在不用它查库所以无事；一旦按店查 `amazon_credentials`（`store_id: String(64)`），`int` 直接对不上。

## 二、目标与边界

**目标（可验收）**

1. 每家店用**它自己的**凭据取数，两店两 seller 数据互不相交。
2. 未授权的店**显式失败**，不返回 mock、不返回空表、不返回别人的数据。
3. 同一进程内两家店并发取数不串 `access_token`。

**明确不做**

- 不新增平台（TEMU / TikTok 是另一件事）。
- 不做增量同步调度（`trade/tasks.py` 的调度策略是独立议题）。
- 不重写 LWA 签名 / 刷新算法（`auth.py` 的签名实现是好的，只缺「按店喂配置」这个入口）。
- 不把选品 / 竞品的假数据改成真数据（它们**依赖**本轮，但各自还要做真实方法实现与同步任务）。

## 三、设计：一条读取口，四个决策

```
调用点（8 处）
   ↓  await
open_data_source(store_id)              ← 新增，唯一入口（async）
   ↓
load_store_credential(store_id)         ← 新增，唯一读取口（async）
   ├─ OAuth 行判断（amazon_credentials）
   ├─ 表单凭据解密（stores_store.api_credentials）
   ├─ access_token 有效性判断（必要时刷新 + 回写）
   └─ 市场映射（participant_id → Marketplace）
   ↓  StoreCredential（store_id / seller_id / marketplace / config）
SpApiDataSource(credential=…, config=…)
   ↓
SPAPIClient(config)  →  SPAPIClientAuth(config)   ← 每店一个实例，自带 token
```

### 决策① 凭据来源优先级

| 方案 | 说明 | 评价 |
|---|---|---|
| **A（推荐）OAuth 优先 → 表单兜底** | `amazon_credentials` 有 `credential_status`、`error_count`、卖家撤销语义；表单无法表达「授权被撤销」 | 语义最强，但要求 OAuth 行**只在 `status=active` 且 `last_refresh_at` 非空**时参与 |
| B 表单优先 → OAuth 兜底 | 与当前唯一有 UI 的路径一致 | 一旦卖家在 Amazon 后台撤销，系统看不出来，会一直用死 token 撞 401 |
| C 按 `updated_at` 取新 | 无需解释优先级 | 时间戳不可比（两条通道的 `updated_at` 更新时机不同），结果是**不可预测**，比选错更坏 |

**取 A**。附加一条硬规则：两条通道都命中且 `refresh_token` 解密值**不一致**时，
打印一条带两个 `updated_at` 的 warning，**不静默选一个** —— 静默选一个等于制造第二份判据。

> 风险与缓解：若线上真实用户全走表单、而 OAuth 表里躺着陈旧行，A 会优先读到陈旧行。
> 上面的「`status=active` + `last_refresh_at` 非空」条件正是为此设的门槛；
> 再加一条：OAuth 行 `error_count >= 3` 时降级到表单并告警（该行已被标记为 error）。

### 决策② 同步栈怎么读凭据（承诺过的岔路口）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）异步前置** | `open_data_source(store_id)` 在 async 栈里读库解密，把**完整 config** 注入数据源；同步方法内部**零 DB** | 8 个调用点要改；`agent_ad._load_ad_rows` 由 sync 改 async |
| B 同步栈内读库 | 线程 + `asyncio.run` + 独立 session，调用点零改 | 每次取数多一次 DB 往返；`_run()` 已经在 `ThreadPoolExecutor` 里 `asyncio.run`，再套一层 session 生命周期；测试极难 patch；与「异步优先」架构逆行 |
| C 进程级凭据缓存 | 授权时写缓存，同步栈只查内存 | 多 worker / 多实例不一致；失效点（撤销、换 token、改密）穷举不完 ⇒ **只能当 token 缓存，不能当凭据来源** |

**取 A**。B 只允许作为「某调用点确实无法异步化」的临时 shim —— 目前**没有这种点**：
`agent_ad` 的 3 个调用点都在 async 方法里（顺带修掉「async 里跑阻塞 IO」这个既有问题）。

### 决策③ access_token 缓存放哪

| 方案 | 说明 |
|---|---|
| T1 不缓存 | 每次取数刷新一次 LWA（1 次 HTTP / 次），会被限流 |
| T2 进程内 per-store 缓存 | 快，但多 worker 各刷一遍；重启丢 |
| **T3（推荐）DB 当缓存** | 读行时看 `token_expires_at`：有效则直接用（省一次 LWA），过期才刷新并回写 |

取 T3，理由：跨 worker 一致、重启不丢、`router.py::refresh_credential` 已经把「刷新 + 回写 + 失败计数」写好了，逻辑可复用。
并发刷新**不加分布式锁**：LWA 刷新是幂等的，多 worker 同时刷新只会多换一个 token，最后写者胜，无副作用。
写回必须用**独立 session**，不能污染调用方事务。

### 决策④ 无凭据时的行为（三态，不许压成两态）

```
DEMO_MODE 且演示店       → MockAmazonDataSource（显式，打日志）
有凭据                    → SpApiDataSource
无凭据（真实客户）        → raise StoreNotConnected（HTTP 409 + code=STORE_NOT_CONNECTED）
```

现在的 `auto` 是「有全局凭据 → 真，否则 mock」，按店后必须废掉这条回退 ——
**给真实客户返回 mock 数据，比报错坏得多**（他会照着假数字补货）。
调用方渲染「该店铺未授权 Amazon」的空态，而**不是空列表**：空列表的意思是「有授权、但没数据」，语义不同。

## 五、验收判据（5 条，全部可执行）

1. **两店不相交**：桩 client 按 config 回放不同订单集 ⇒ 两店 `fetch_daily_sales` 的订单号集合交集为空。
2. **不读全局**：删掉 `.env` 的 `SPAPI_REFRESH_TOKEN` 与 `SPAPI_AWS_*` 后，两家店仍能取数（证明凭据只来自 DB）。
3. **未授权硬失败**：无凭据店铺 ⇒ `StoreNotConnected`，且**不产出任何行**（断言异常类型 + 断言没有 mock 行落库）。
4. **配置真的进去了**：`data_source._client.auth.config.lwa.refresh_token` == 该店密文解密值（防「传了 config 但传错店」）。
5. **反向注入**：① 把 loader 的优先级反过来 ⇒ 用例 1 必须变红；② 把 `store_id` 从查询里去掉（恒取第一家）⇒ 用例 1 必须变红。

> 判据 4 是关键：它挡的正是 1.1 那种「看起来注入了、其实注入了空值」的形态。

## 七、风险与回滚

| 风险 | 说明 | 缓解 |
|---|---|---|
| **半开关状态** | mock 现在覆盖着一切；改一半会让一部分调用点抛异常 | 8 个调用点**同一批**提交；删掉旧工厂，漏改立刻 `ImportError`/`TypeError` 而不是静默 mock |

一旦某处读不到开关就退回旧行为 —— 本仓已经踩过「条件挂载 ⇒ 门禁根本没挂」。
回滚手段是 `git revert`，不是运行时开关。

### 本轮额外修掉的两处「顺手会踩」的东西

1. **`_guard` 会把 409 吞成 500**（`modules/review_analyst/router.py`）
   `except Exception → HTTPException(500)` 在旧世界里没被踩到，因为旧工厂**从不抛**
   （没凭据就静默 mock）。接上按店凭据后，第一个真实客户在没授权的店上点「复盘」
   看到的是 `利润审计失败: 店铺 store_xxx 未授权`（500）—— 归因指向服务端。
   修法：`StoreNotConnected` / `UnsupportedMarketplace` **原样上抛**，映射只在
