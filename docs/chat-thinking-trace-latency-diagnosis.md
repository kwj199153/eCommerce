# 对话「无思考过程 + 10 余秒空窗」诊断

第 216 轮排查。问题原话：*「为什么这个问题没有思考链的展示，但是却思考了 10 多秒」*

## 一、结论速览

两件**互不相关**的事叠在同一屏上，所以看起来像一个故障：

| 疑问 | 真相 |
|---|---|
| 为什么没有思考链展示 | 界面上的「思考过程」**不是模型的思考链（CoT），而是工具调用轨迹**。本轮一个工具都没调 ⇒ 轨迹必然为空 |
| 为什么思考了 10 多秒 | 确实调了模型，但**模型边生成边吐的 token 全被丢弃**，正文只在最后一次性下发 ⇒ 这 10 多秒前端收不到任何字节 |

## 二、证据：14.9 秒的去向

`rid = c22fae2240a64912`，`query='你可以做什么'`，`tools=-`，`actions=0`，`cost=14925.3ms`。

| 时刻 | 事件 | 增量 |
|---|---|---|
| 08:19:11.714 | 请求进入（鉴权 / 限流 / 归属查询） | — |
| 08:19:11.932 | 上下文裁剪完成：轮 21，估算 12,465 → 5,817 token | 0.22 s |
| 08:19:13.341 | 真正发出 HTTP 到 DashScope | +1.41 s（Agent 初始化 + 技能目录查询 + 拼 tools） |
| 08:19:17.998 | 收到响应头 = **首字节 TTFT** | +4.66 s |
| 08:19:26.732 | 整轮结束 | +8.73 s（流式生成正文） |
| | **合计** | **14.93 s** ✅ 与日志 `cost=14925.3ms` 吻合 |

模型侧发起的是流式请求（`'stream': True`）—— 也就是说 token 是**边生成边到达后端**的。

## 三、为什么轨迹为空（代码级链）

```
ThinkingTrace.vue  ←  msg.thinkingSteps
                        ↑ 唯一写入点 stores/chat.ts::appendThinkingStep
                        ↑ 消费 event: step
                     ai_infra/sse.py::ToolTrace.feed()
                        ↑ 只翻译 on_tool_start / on_tool_end
                        ↑ docstring：「非工具事件（模型 token 流等）原样放过」
        ⇒  没调工具  =  没有 step  =  面板没有东西可渲染
```

`route_stream` 的另一半下发口是 `progress()`：单行、**会被覆盖**、`setLoading(false)` 时清空。它只负责把「AI 正在思考…」换成具体阶段文案，**从不累积**，因此永远长不成「思考过程」。

## 四、真·思考链为什么也看不到

全仓检索 `reasoning_content` / `enable_thinking`：**0 个文件命中**（生产代码、测试、配置全无）。`ai_infra/base_agent.py::_get_default_llm` 构造 `ChatOpenAI` 时只传 model / key / base_url / temperature / max_tokens / timeout，既不请求思考模式，也不读 `additional_kwargs`。且默认模型 `qwen-max` 本身不是思考模型。

⇒ 即便模型有内部推理，它也没有任何一条通道进入本系统。

## 五、顺带发现（需另行验证）

同一会话连续三轮的消息统计：

| 轮次 | user | assistant | tool |
|---|---|---|---|
| 轮 19（08:16:52） | 19 | 29 | 13 |
| 轮 20（08:17:52） | 20 | 29 | 13 |
| 轮 21（08:19:11） | 21 | **29** | 13 |

每轮 `user` +1 而 `assistant` **冻结在 29**，历史尾部出现连续 U（`…A U` → `…A U U` → `…A U U U`）。
轮 19、20 有「上下文裁剪」日志却**没有收尾日志**（`决策层B LLM 兜底` 未打印）⇒ 那两轮未正常跑完，且全程无 ERROR/WARNING。

**未验证**：中断的确切原因；以及「连续同文 user」是否与用户等待空窗后重发有关。需单独一轮查。

## 六、可选修复方向（未执行，待拍板）

| 优先级 | 方案 | 说明 |
|---|---|---|
| P0 | 把 `on_chat_model_stream` 的 token 增量下发给前端 | 治「14.7 s 零输出」的根。前端已有「就地替换最后一条正文」的机制（`replies/secretary.ts`），增量先显示、最终用 state 正文替换即可，不动「正文唯一取口」的约束 |

| P3 | 接真·思考链（换思考模型 + 采集 `reasoning_content` + 新增事件通道） | 这是**新增能力**，不是修 bug |

## 七、方法教训

排查中我先用「`content` 长度 ≤ 26 字符」的窄正则统计消息角色，得出「17 条全是 user、0 条 assistant」的结论 —— 而真相是 21 user / 29 assistant / 13 tool（assistant 回复都是长文本，被我的过滤条件整批排除了）。

**测量用的正则，其过滤条件本身就是偏差源。** 计数类判据不要附带与结论无关的条件。
