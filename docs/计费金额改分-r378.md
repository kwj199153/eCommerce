# 计费金额「元 → 分」全链路改造（第 378 轮）

> 起因：老板原话「billing 单位改成分（目前是元）」，并拍板
> 「参考 eeducation 项目，应该是**全链路**」「参考 eeducation 项目做法」。
>
> 结论先说：**收款金额从「float 元」整体切成「整数分」**，链路是
> `数据库列 → 计价函数 → 网关 DTO → 支付宝适配 → 结算比对 → API 契约 → 前端渲染`。
> 全项目只有**两个**换算出口：后端 `backend/core/money.py`、前端
> `frontend/src/api/billing.ts::fenText`。其余任何地方都不许再出现 `/100` 或 `*100`。
> 真机 12 条判据全绿（截图见 `.workbuddy/probes/out/billing-fen-*.png`）。

---

## 1. 为什么非改不可（不是洁癖，是两个"不会报错"的缺陷）

改前：`invoices.amount` = `double precision` 元，`subscription_plans.price_monthly` = `double precision` 元。

| 缺陷 | 具体表现 | 为什么门禁看不见 |
| --- | --- | --- |
| ① 折算漂移 | 年付 = 月付 × 10。月付一旦是小数，乘完就带 `2999.0000000000005` 这种尾巴；每加一步运算都在赌"它恰好没漂" | 漂了也是"约等于对"，业务上照常成功 |
| ② 比对只能带容差 | 支付宝回调给的是**元字符串** `"2990.00"`，本地是 float ⇒ 对账只能写 `abs(a-b) < 0.01` | **少收一分也算对账通过**。这不报错，它只是把钱少了 |

存整数分之后：折算全在整数域（`yearly_price(29900) == 299000`，精确），
与网关回调的比对是 `int == int`（**零容差**），元形态只存在于两个出口函数的入参/出参上。

### 1.1 一个**刻意**的例外：`subscriptions.llm_cost_used` 保持 Float 元

单次 LLM 调用常见 0.0003 元 = 0.03 分。存整数分会四舍五入成 **0** ⇒ 计量归零、
成本报表全 0，比浮点误差危险得多。所以这一列**不动**，并在模型上写了长注释
说明"这不是漏改"。单测里有一条判据专门守着它（`test_llm_cost_used_stays_float`）。

### 2.1 为什么换算出口放 `core/money.py` 而不是 `modules/billing/pricing.py`

`platforms/payment/alipay.py` 是**外部适配层**，本仓约定它不许 import 业务模块
（`modules/billing/*` 属计费域）。放 `core/` 之后，适配层与业务层引用的是**同一份**
实现，而不是各自复制一份 —— 后者迟早会分叉（一边四舍五入、一边截断）。

### 2.2 显示口径（与 eEducation 逐字一致）

`fenText(29900)` → `¥299`（**整数不带 `.00`**），`fenText(299050)` → `¥2990.50`。
核对过 eEducation 的 `fenText`（`frontend/src/api/billing.ts:263`），规则相同：
`¥ + (Number.isInteger(yuan) ? String(yuan) : yuan.toFixed(2))`。
所以账单表里显示的是 `+¥2990` / `+¥299`，**不是** `+¥2990.00` —— 这是参照项目的既有口径，不是本轮的选择。

## 3. 迁移：顺序错了会把 300 元变成 300 分

```python
op.alter_column(table, old, new_column_name=new)          # ① 先改名（值仍是元）
op.execute(f'ALTER TABLE {table} ALTER COLUMN {new} '
           f'TYPE integer USING round({new} * 100)::int') # ② 再换类型并 × 100
```

反过来的话（先换类型再改名）`USING` 会在"还叫 `amount` 的元值"上跑，
300.0 → `round(300*100)` 没问题，但若写成 `USING amount::int` 就会**把 299.5 元截成 299 元**。
一次只做一步，才能保证 `USING` 的输入是元。

**幂等守卫**：`create_all()` 用当前模型建表 ⇒ 全新库上列本来就叫 `amount_fen` 且已是 integer。
所以每一步都先 `sa.inspect` 看「列在不在 / 类型是不是浮点」，已就位就跳过。

**可逆性实测**（不是"应该有 downgrade"，是真跑过三段）：

| 阶段 | `subscription_plans` | `invoices` |
| --- | --- | --- |
| `upgrade head` | 0 / 29900 / 99900 | 29900 / 29900 / 299000 / 299000 |
| `downgrade -1` | 0.0 / 299.0 / 999.0 | 299.0 / 299.0 / 2990.0 / 2990.0 |
| `upgrade head` 再来一次 | 0 / 29900 / 99900 | 29900 / 29900 / 299000 / 299000 |

迁移前列类型为 `double precision`、迁移后为 `integer` / `NOT NULL` / default `0`；
迁移前把数据备份到 `.workbuddy/backup/fen-migration-20261017/before.json`。

### 4.1 新增判据都在防什么（`test_billing_units.py` 25 条，摘要）

- 模型列必须是 `Integer` 且列名带 `_fen`，**旧列必须不存在**（三态都判，否则"加了个新列、老列还在写"看不出来）
- `llm_cost_used` **必须仍是 Float**（防"顺手全改成整数"把计量归零）
- 网关 DTO **不许有裸 `amount`**（这一条最要紧：只改模型不改 DTO ⇒ 网关把元当分落库、差 100 倍且零报错）
- `amount_matches` 零容差 —— 行为判据 + **AST 断言函数体内没有 `abs`**（读源码字符串会被 docstring 骗过）
- 支付宝 `charge` 必须调用 `fen_to_yuan_text` 且**函数体内没有 `round`**（防第二处换算）
- `router.py` 的 dict 键不许出现 `amount` / `price_monthly` / `price_yearly`

## 5. 反向注入：两次都抓到了缺陷，其中一次抓的是我自己的探针

**不是"跑绿了所以信它"，是先证明它会红。**

| 注入 | 内容 | 期望 | 实测 |
| --- | --- | --- | --- |
| **M1** | `api/billing.ts`：`const yuan = abs / 100` → `const yuan = abs`（漏除 100） | 大面积转红 | **7/12 FAIL**，退出码 1 |
| **M2** | `Subscription.vue`：账单单元格绕过 `fenText`，直接渲染 `record.amount_fen` | 账单相关转红 | **2/12 FAIL**，退出码 1 |

两次注入后都用备份还原并用 `sha256sum -c` 双向校验，`grep -rn REVINJ frontend/src` = 0。

### 5.1 M1 抓到的是**探针自己的假绿**

第一版横幅判据写成 `cards.banner.startsWith(EXP_BANNER)`。M1 注入后横幅实际显示
**`¥29900/月`** —— 但 `"¥29900".startsWith("¥299") === true` ⇒ **判据 PASS**。

前缀匹配对「多两个 0」这类缺陷天生失明，而那恰恰是这一轮**唯一**要防的缺陷。
已改为从文本里抽 `^¥[\d.]+` 再**精确相等**；改完 M1 下该条正确转红（`{"text":"¥29900/月 正常","price":"¥29900","exp":"¥299"}`）。

> 这条值得单独记：门禁读数是绿的，不代表它看过；只有反向注入能把"它根本没在判"暴露出来。

### 5.2 M2 抓到了一条旁路，顺手补了一条形态判据

M2 把单元格改成直接渲染 `record.amount_fen`，读数变成 `+299000`。这时：

- **逐行比对抓到了**（`+299000 ≠ +¥2990`）✔
- **反例扫描没抓到** ✘ —— 反例正则找的是 `¥ + 分值`，而绕过 `fenText` 之后单元格里**连 `¥` 都没有**

于是补了第 7 条**形态判据**：每个金额单元格必须是 `符号 + ¥ + 数字`。
这一条与逐行比对互为独立锁：前者防"值算错"，后者防"绕过唯一换算点"。
补完之后 M2 下变成 **2 条红**。

## 7. 一句话交接

金额只有两种形态：**库里/接口里是分（int），界面上是元（fenText）**。
在这两者之间加任何一处 `×100` / `÷100` 都是缺陷 —— 门禁会红在
`check-billing-pay-flow.cjs` 的 D3/D5、`test_billing_units.py` 的 AST 断言，
以及 `cdp-billing-fen.mjs` 的整页反例扫描上。
